# SQL-тесты (pgTAP)

Интеграционные проверки инвариантов БД против **локального** Supabase
(удалённый проект `qgmnxrgtlpyqglwqmsej` не трогаем).

## Запуск

```bash
supabase start                 # локальный стек (Docker)
supabase db reset              # применить все миграции с нуля
supabase test db               # прогнать pgTAP из supabase/tests/*.sql
```

`supabase test db` оборачивает каждый файл в транзакцию и откатывает —
данные не остаются.

## Что покрыто

- `idempotency.test.sql` — дважды вызывает настоящий `pay_order` с одним
  `p_payment_uuid` и проверяет один payment, один номер чека и один op_log.
- `cash_limit.test.sql` — проверяет границу 6 000 ₪, разрешённые 10%, запрет
  обхода через private RPC и отсутствие финансовых строк при отказе.
- `rls_scope.test.sql` — под ролью `authenticated` и JWT org A проверяет
  cross-org SELECT, запрет UPDATE чужого устройства и UPDATE собственной строки.
- `telemetry_ingest_boundaries.test.sql` — серверные границы приёма телеметрии
  (170): принадлежность `device_uuid` тройке org + location + auth_user_id,
  недоверенный JSON (битый элемент не валит пакет), лимиты и насыщение
  счётчика повторов, права на `client_errors`/`ops_errors` и то, что
  отвергнутый вызов не запускает 30-дневную очистку.
- `telemetry_missing_fields.test.sql` — обязательные строковые поля элемента:
  отсутствующий ключ, JSON `null`, object/array/number/boolean вместо строки
  и пустой `fingerprint`, каждый случай до и после валидного соседа. Битый
  элемент не должен ни ронять пакет, ни обнулять соседа; пределы 20/дедуп/
  `count` проверяются там же, чтобы правка не ослабила их.

## Конкурентность

Часть инвариантов одной транзакцией не проверяется: pgTAP не показывает двух
клиентов, гонящихся между `COUNT` и `INSERT`. Для них есть отдельные драйверы
на настоящих соединениях. Они работают **только** на одноразовой локальной БД
и отказываются стартовать на любой другой — имя базы проверяется регулярным
выражением.

```bash
# одноразовая БД с применёнными миграциями (пример имени — guard требует
# префикс kassa_f62_); существующие базы и контейнеры не трогаются
node scripts/test-telemetry-ingest-concurrency.mjs kassa_f62_<suffix>

# чистые тесты самого guard, без Docker и без подключения к БД
node --test scripts/test-telemetry-ingest-concurrency.test.mjs
```

Драйвер телеметрии сам засевает синтетическую организацию/точку/устройство и
удаляет их в конце — в том числе когда сценарий упал. Он ставит два соединения
на общую стартовую блокировку и отпускает их одновременно, предварительно
убедившись по `pg_locks`, что оба соединения действительно прошли барьер и
стоят на конкретной блокировке спорного участка (пауза внутри `INSERT`,
собственный ключ `org + device` или конфликт строки), а не просто «ждут
чего-нибудь».

Проверки точные, потому что мягкой проверки «строк не больше 100» мало:
мутация лимита на `v_today >= 99`, при которой теряются оба новых события,
её проходит. Сценарий фиксирует состояние до (ровно 99), после (ровно 100),
сумму принятых элементов (ровно 1), число новых `fingerprint` (ровно 1) и
сохранность 99 засеянных строк; значения читаются из ответов самих рабочих
соединений. Повтор одного `fingerprint` даёт одну строку, `count` 1+3+4=8 и
две единицы в ответах RPC. Каждый сценарий прогоняется дважды, состояние
до/после печатается в каждой строке; `TELEMETRY_TRACE=1` дополнительно
печатает наблюдаемые состояния блокировок.

## CI

`online_order_composition.test.sql` — серверная граница состава гостевой
заявки (171): минимум и максимум групп модификаторов, обязательность размера
и сохранённые инварианты 116 (чужой и недоступный модификатор, предел 10
различных модификаторов, серверный расчёт цены, идемпотентность по
`client_uuid`, лимит частоты заявок).

pgTAP требует локальный Supabase и Docker, поэтому не входит в `npm test`.
Workflow `.github/workflows/ci.yml` поднимает отдельный локальный стек,
применяет миграции с нуля и запускает эти тесты на каждый push/PR. Удалённый
проект при этом не затрагивается. Фронтенд-инварианты (округления денег, офлайн-идемпотентность,
scope-карантин, drain waiting_auth, длинный чек, optimistic rollback) покрыты
vitest-тестами в `src/`.
