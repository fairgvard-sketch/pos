# Онлайн-заказы и QR-меню (050–099)

Один публичный поток обслуживает три сценария:

- QR конкретного стола — стол определяется автоматически, имя и телефон не
  спрашиваются, принятая заявка становится дозаказом в счёт стола;
- QR стойки или обычная ссылка — гость выбирает «здесь / с собой / доставка»,
  оставляет контакт и получает отдельный counter-заказ;
- ссылка с сайта/соцсети — тот же интерфейс с атрибуцией `order_channel`.

Оплаты и уведомления через WhatsApp/Telegram в этот этап намеренно не входят.
Существующий фискальный контур не меняется: когда оплата нужна, чек по-прежнему
рождается через обычный `pay_order`.

## Архитектура

```
Гость (телефон)                Supabase                       Касса (T2)
/order/<location_id>  ──POST──▶ Edge Fn public-order ──rpc──▶ online_orders (staging)
       │                          (service_role)                   │ realtime
       │◀─GET (поллинг 5с)─ Edge Fn public-order ◀─rpc─┐           ▼
       │                                               │      экран /online
/order меню ◀────GET──── Edge Fn public-menu           │      Принять ──▶ accept_online_order
                                                       │            ├──▶ place_order (без стола)
                                                       └──── статус  └──▶ open table + append
                                                                          (QR стола)
```

Ключевые решения:

- **Анонимный гость ≠ устройство кассы.** Гость ходит только в Edge Functions
  (anon-ключ как bearer); прямого доступа к таблицам нет. Вся валидация, цены,
  идемпотентность и анти-спам — в `submit_online_order` (SECURITY DEFINER,
  EXECUTE только у service_role).
- **Часы приёма (112, 116):** окно приёма задаёт расписание
  `settings.online_orders.hours` — оно же ограничивает время заказа «на потом».
  Заказ «как можно скорее» требует открытых часов сейчас (POS-точке вдобавок
  открытую смену — приёмка живёт на кассе); предзаказ «ко времени» — только
  попадания `pickup_at` в будущее окно, поэтому закрытая точка продолжает
  принимать заявки на завтра. Нет расписания — приём в любое время.
  Подробнее — «Часы работы» ниже.
- **Заявка ≠ заказ.** Снапшот позиций и цен хранится в `online_orders` для
  карточки кассира; настоящий заказ или дозаказ создаётся только при принятии
  через `place_order` либо `open_or_get_table_order` + `append_to_order`.
  Цены пересчитываются из каталога заново, остатки списываются триггерами 047,
  стоп-лист уважается на этапе заявки.
- **Неоплаченный принятый заказ** (гость не пришёл) закрытие смены аннулирует
  как брошенный counter-заказ (035), остаток вернёт триггер 047.
- **Анти-спам в БД:** ≤3 заявок с одного телефона за 15 минут, ≤30
  необработанных заявок на точку, лимиты длины полей, ≤30 позиций.
- **client_uuid** генерирует страница гостя: ретрай POST не создаёт дубликат,
  он же — «секрет» для поллинга статуса и client_uuid будущего заказа.
- **QR стола не содержит `table_id`.** В URL идёт отдельный UUID
  `tables.public_token`; Edge Function и БД проверяют точку, активность и
  статус стола, после чего снапшотят label.
- **UX гостя:** поиск по меню, корзина с TTL 6 часов, table-context на каждом
  критическом экране, рекомендации из других категорий и декоративное
  autoplay-видео hero (`muted`, `loop`, `playsInline`, poster из шапки).

### Слаг точки (106)

Первый сегмент после `/order/` — либо `location_id`, либо человекочитаемый
слаг: `menu.angle.co.il/order/bulochka`. UUID остаётся полноправным входом,
потому что QR со старыми ссылками уже наклеены на столы; слаг — только
дополнительный вход, а не замена.

- Владелец задаёт слаг в бэкофисе → `set_location_slug` (право `manage`,
  capability `public_menu`). Пустая строка снимает слаг.
- Занятость и формат проверяет БД: уникальный индекс на `location_slugs`,
  CHECK на формат и таблица `reserved_slugs` со служебными именами.
- Гость резолвит слаг через `resolve_location_slug` — единственную функцию,
  доступную анону. Она отдаёт только `location_id`; витрину по нему выдаёт
  `public-menu` со своими capability-гейтами.
- Edge Functions продолжают принимать **только UUID**: резолв делает фронт
  в `publicApi.resolveLocationId` до вызова API. Это сознательно — иначе
  проверку слага пришлось бы дублировать в `public-menu`, `public-order` и
  `public-reserve` во всех местах, где они валидируют `loc`.

## Поведение кассы

- Новая заявка: звонок + тост на любом экране, счётчик на пункте «Онлайн».
- «Принять» — нужна открытая смена (иначе подсказка). Печатается кухонный
  тикет (если включён в настройках кассы), заказ виден бариста.
- «Отклонить» — с необязательной причиной, гость увидит её на странице.
- «Оплатить» при получении — обычный PaymentSheet (наличные/карта/кошельки,
  смешанная), чек — как всегда («Как выдать чек?» / автопечать).
- «Отменить» принятый (гость передумал) — право `void_order`, остаток вернётся.
- Вкладка «История» (113): прошлые заявки за период (сегодня / 7 / 30 дней) с
  поиском по имени и телефону. Активный экран по-прежнему показывает только
  новые и решённые за сутки — горячий поток не удлиняется.

### Лояльность в онлайн-заказах (113)

`accept_online_order` находит гостя по `customer_phone` заявки (телефон
нормализуется к одним цифрам, как в 031) и проставляет `orders.guest_id`.
Начисление не меняется: штампы и баллы даёт `pay_order` (046) в момент
оплаты по `guest_id`. Правила:

- гость заводится только при включённой программе (`loyalty_mode <> 'off'`);
- имя из заявки не затирает уточнённое кассиром (`COALESCE`);
- ручная привязка гостя на открытом счёте стола приоритетнее автоматической;
- награда (бесплатный напиток / списание баллов) по-прежнему выбирается
  кассиром через `apply_loyalty` — автоматически ничего не списывается.

## Self-service для любого клиента (051)

ANGLE → QR menu → Online orders (со 107 настройки канала живут
только в бэкофисе; раньше — POS Настройки → Обслуживание): тумблер приёма (сервер
отклоняет заявки кодом `disabled`, витрина `public-menu` отдаёт
`accepting` — гостевые страницы прячут оформление заранее; организация
без модуля `online_orders` отклоняется раньше кодом `module_disabled`,
см. «Продуктовые модули» в `database.md`), готовая
ссылка `/order/<location_id>` с копированием и печать QR-флаера на
встроенном термопринтере. Владелец новой точки включает онлайн-заказы
сам, без разработчика: завёл меню → распечатал QR → повесил на стойку.

### Чистая витрина без модуля заказов (100, capability-гейты 105)

С 105 витрину и корзину гейтят capabilities (`org_public_menu_gates`):
`public_menu` дают и ANGLE Menu, и ANGLE Orders (без покупки Menu);
корзина/приём/статус заявки — `online_orders`. Отказ — стабильный
`module_disabled` до settings-тумблеров; `get_online_order_status` —
защищённое чтение (закрывается вместе с продуктом).

Организация с capability `public_menu`, но без `online_orders` (ANGLE
Menu без POS/заказов) получает ту же гостевую страницу в режиме витрины:
`public-menu` отдаёт `location.modules.online_orders=false`, страница
скрывает корзину, чекаут, пилл типа заказа и баннеры «закрыто/пауза»
(смен у digital-only организации не бывает — вечное «закрыто» вводило бы
гостя в заблуждение). Тап по товару всегда открывает карточку с
описанием и ценами, без добавления в корзину. Старые клиенты без поля
`modules` работают как раньше. Хелпер — `isViewOnlyMenu` в
`src/features/online/publicApi.ts`.

Для встраивания меню в сайт ресторана `vercel.json` задаёт явную
frame-политику: `/order/*` и `/reserve/*` отдают
`Content-Security-Policy: frame-ancestors *` (страницу можно класть в
iframe любого сайта), остальные маршруты POS — `frame-ancestors 'self'`.

### Standalone-режим без POS (101)

«Точка принимает заказы» отделено от «на кассе открыта смена»:

- `online_fulfilment_mode(org, settings)` — режим обслуживания:
  `pos` (как раньше, смена обязательна, приёмка на кассе) или
  `standalone` (веб-инбокс кабинета). Явная настройка
  `settings.online_orders.fulfilment`; дефолт — по модулю `pos`.
- Доступность standalone-точки: тумблер + пауза + недельное расписание
  (см. «Часы работы» ниже). `is_open` гостя у standalone не зависит от смен.
- Жизненный цикл standalone: `new → accepted → preparing → ready →
  completed` (+ `rejected` из new, `cancelled` из активных).
  Переводы — `set_online_order_status_web`: только owner/manager-членство,
  только standalone-режим, заявки с `order_id` неприкасаемы — веб не
  трогает финансовый контур POS; атрибуция в `decided_by_member`.
- POS-режим не изменился: `accept_online_order` конвертирует заявку в
  настоящий заказ со сменой и PIN-сессией, как раньше.
- Гостевой статус-экран понимает оба цикла; у standalone-заявки нет
  номера дня (`daily_number` только у POS-заказа).

pgTAP: `standalone_online_orders.test.sql`. Веб-инбокс живёт в репо
`anglesite` (раздел Orders), realtime-подписка использует публикацию и
RLS-чтение из 050.

### Номер заявки (139)

У заявки есть собственный человеческий номер `order_number` — сквозной в
пределах точки и не сбрасывающийся по дням. До 139 назвать заявку было
нечем: кабинет показывал хвост UUID, гость standalone-точки не видел
ничего, а `daily_number` появляется только после конверсии в POS-заказ и
обнуляется каждую ночь.

- нумерация идёт с 1001: четырёхзначный номер сразу читается как номер
  заявки и не путается с дневным номером кассы;
- у каждой точки счётчик свой (`online_order_counters`, атомарный upsert —
  тот же приём, что у `order_counters` в 004);
- номер ставит триггер `trg_online_orders_number`, а не
  `submit_online_order`: функция приёма переписывалась восемь раз, и каждое
  повторение её тела — риск потерять восстановленный гейт (так уже было в
  058). Триггер закрывает все пути вставки, включая будущие;
- у POS-заявки два номера, и они означают разное: `#1042` — заявка,
  `#43` — заказ на терминале. Оба честно показываются рядом;
- `get_online_order_status` отдаёт `order_number` гостю; `public-order`
  возвращает ответ RPC как есть, поэтому поле доезжает без правки функции.
  **Гостевая страница и экран кассы номер пока не показывают** — это
  отдельная правка UI, см. «Отложено осознанно».

### История заявки (140)

`online_order_events` — append-only журнал переходов: что произошло, когда,
кто (`guest` / `backoffice` / `pos` / `system`) и по какой причине. Раньше
у заявки хранилось только последнее решение (`decided_at`), поэтому после
«Готово» нельзя было ответить, когда её приняли и сколько она готовилась.

Пишет триггер `trg_online_orders_events`, а не вызывающие функции, — в
журнал попадают и касса (`accept_online_order`/`reject_online_order`), и
кабинет (`set_online_order_status_web`), и любой будущий путь. Правки без
смены статуса (лояльность, привязка заказа) историю не засоряют.
Клиенту доступно только чтение (RLS по организации, как у самих заявок).

Бэкфилл честен по объёму знаний: у заявок, созданных до 140, есть
«получена» и последнее решение. Промежуточные шаги не восстановимы, и
придумывать их нельзя — лента такой заявки просто короче.

Персональные данные в журнал не пишутся: имя автора — это `display_name`
веб-члена или имя сотрудника кассы, почты и телефона там нет.

### Рабочий стол кабинета (141)

`get_online_orders_web(location, scope, …)` — один вызов на весь экран
раздела Orders: строки нужного разреза, счётчики вкладок, режим точки,
контекст кассы и право на действие.

| Разрез | Что попадает |
|---|---|
| `active` | работа текущего дня точки: заведённые сегодня плюс предзаказы, которые выдавать сегодня |
| `older` | незакрытый долг: заведено раньше, время выдачи прошло |
| `scheduled` | предзаказы на будущие дни (`pickup_at` за пределами дня) |
| `all` | любая заявка в окне дат: фильтры, поиск, пагинация |

Разрезы взаимоисключающие и в сумме покрывают все активные заявки, поэтому
счётчики вкладок не пересекаются. День считается в часах ТОЧКИ, а не
браузера: владелец в другом поясе видит день своего заведения.

Что функция закрывает помимо запросов:

- **`can_manage` вместо догадки клиента.** Кабинет выводил право на
  действия из списка продуктов, и это правило расходилось с серверным:
  член организации с ролью `accountant` видел кнопки «Принять»/«Отклонить»
  и получал `backoffice access denied`. Теперь право считает сервер по тем
  же условиям, что и `set_online_order_status_web` (роль `owner`/`manager`
  плюс standalone-режим точки);
- **контекст кассы** для POS-точки: `pos.shift_open` — единственная честная
  причина, почему заявку на терминале ещё никто не видит;
- **история без потолка**: раньше кабинет читал «последние 30 дней, максимум
  200 строк» без пагинации и серверного поиска — заказ двухмесячной
  давности найти было нечем.

Ссылки «открыть на кассе» функция не отдаёт и отдавать не может: маршрут
`/online` в POS требует аккаунт устройства и PIN-сессию и не принимает
идентификатор заказа. Честный хендофф — номер заявки, номер заказа на
терминале и его состояние.

#### Что считается незакрытым (142)

`accept_online_order` ставит заявке `accepted` и привязывает настоящий
заказ кассы. Дальше жизнь идёт в `orders` — оплата, выдача, закрытие
смены, — а строка `online_orders` **навсегда остаётся `accepted`**:
двигать её больше нечему. В 141 такая заявка наутро попадала в «Older
unresolved», и владелец POS-точки видел список давно отданных заказов с
требованием «закройте или отмените их», которого не мог выполнить:
веб-запись для POS-точки запрещена (`pos_mode`).

С 142 правило простое: **заявка с `order_id` — не долг кабинета**. Её
судьба решена в момент приёмки, состояние настоящего заказа видно в
панели (`pos_daily_number`, `pos_status`), а сама заявка остаётся в «All
orders» и находится поиском. Работы текущего дня это не касается:
сегодняшняя принятая заявка по-прежнему в «Active» с подписью «на кассе
как заказ #43». Долгом остаётся то, что им и является — заявка `new`,
которую на кассе не приняли и не отклонили.

Данные не переписывались: изменился ответ на вопрос «что показать», а не
статусы. Подсказка блока тоже разная по режиму — POS-точке кабинет не
советует того, чего она из кабинета сделать не может.

pgTAP: `online_orders_desk.test.sql` (номера, история, разрезы, право,
поиск, пагинация, чужая точка, принятое на кассе вне долга).

### Часы работы — окно приёма заказов (112)

`settings.online_orders.hours` — единственный источник «когда точка
принимает заказы»: ключ — день недели (`0` = воскресенье) в таймзоне
точки, значение — окна `[["08:00","20:00"], …]`. Конец меньше начала =
переход через полночь (`20:00–02:00`). **Нет ключа или `null` — приём в
любое время; день без окон — закрыт.** Точки, которые расписание не
настраивали, поведения не меняют.

Расписание ограничивает и «сейчас», и **выбранное гостем время**. До 112
последнее не проверялось вовсе (только «не в прошлом» и «не дальше 24
часов»), поэтому заявку можно было оформить на 23:30 при закрытии в 20:00.

- `online_hours_open_at(settings, tz, at)` — ядро проверки на произвольный
  момент; `online_hours_open(settings, tz)` осталась как обёртка с `NOW()`.
- `submit_online_order`: часы — общий гейт приёма для **всех** точек,
  включая POS (раньше только standalone). Открытая смена его не отменяет:
  смена решает, идёт ли приёмка на кассе, часы — примем ли заявку вообще.
  Смена, открытая дольше часов, работу кассы не меняет.
- `pickup_at` вне часов → `pickup_outside_hours`. Лимит 24 часов сохранён.
- `public-menu` отдаёт `location.hours` и `location.timezone`; `is_open`
  учитывает часы у всех точек (у POS — вместе с открытой сменой).

#### Предзаказ вне часов работы (116)

112 проверял расписание только на `NOW()`, поэтому закрывшееся заведение
переставало принимать и заказы **на завтра**: витрина предлагала слоты
завтрашнего окна, а `submit_online_order` падал с `closed` ещё до проверки
`pickup_at`. Приём пропадал ровно тогда, когда предзаказ нужнее всего —
ночью и в выходной. С 116 гейт разделён по смыслу:

- `pickup_at IS NULL` («как можно скорее») — требует, чтобы точка была
  открыта **прямо сейчас** (POS — плюс открытая смена): готовить некому;
- `pickup_at IS NOT NULL` (заказ ко времени) — требует, чтобы точка была
  открыта **в этот момент**. Часы «сейчас» и смена роли не играют: смысл
  предзаказа в том, что его оформляют заранее.

Прошедшее `pickup_at` нормализуется в «сейчас» **до** гейта, иначе заявка
на минуту назад считалась бы предзаказом и обходила проверку. Лимит 24
часов сохранён, поэтому горизонт предзаказа не расширился. Заказ за столом
(`table_token`) остаётся строго «сейчас»: гость сидит в зале. Пауза (054) и
выключенный приём (051) запрещают и предзаказ — это ручное «мы не
принимаем», а не расписание.

`public-menu` рядом с `is_open` («открыто сейчас») отдаёт **`preorder`** —
есть ли впереди хоть одно окно расписания. Витрина по нему оставляет
оформление доступным: чип «Как можно скорее» блокируется, форма сразу
открывается на выборе времени, предупреждение меняется с «приём
приостановлен» на `pubClosedPreorder`. Старая edge function поля не
отдаёт — тогда поведение прежнее, по `is_open`.
- Гость выбирает время из слотов, а не свободным вводом:
  `src/features/online/pickupSlots.ts` строит сетку 15 минут внутри окон на
  сегодня и завтра (таймзона точки через `Intl`, поэтому переход на летнее
  время учитывается). Пустой список — чип «Ко времени» недоступен.
- Окно общее на все типы заказа: отдельных часов для доставки нет. Формат
  `hours` — объект, так что разбивку по типам можно добавить ключом без
  слома сохранённых настроек.

Редактор — веб-кабинет, «QR menu» → «Opening hours» (строка на день,
сводка вида `Sun–Thu 08:00–20:00 · Fri 08:00–14:00`). В кассе редактора
нет: часы — настройка уровня точки, она переехала в бэкофис вместе с
остальными (107).

pgTAP: `order_hours.test.sql`; unit — `pickupSlots.test.ts`.

Там же — соцссылки (Instagram / Facebook / отзыв в Google): хранятся в
`locations.settings.online_orders`, `public-menu` отдаёт их в
`location.links`, гостевая страница показывает кнопки в подвале главного
экрана (пустая ссылка — кнопки нет).

### Те же настройки из бэкофиса

Веб-кабинет владельца (репо `anglesite`, раздел «QR menu»)
правит тот же `locations.settings.online_orders` через
`patch_location_settings_web` (091): раздел в allow-листе функции и
мержится поключево, поэтому кабинет шлёт только изменённые ключи.

Два места правки — сознательно: сотрудник на смене должен уметь
остановить приём заказов, не заходя в веб. Разделение по возможностям
устройства:

| | Касса | Бэкофис |
|---|---|---|
| Тумблер, типы заказа, витрина, видео, соцссылки | да | да |
| Загрузка шапки/фона | да | нет (Storage-аплоад живёт в кассе) |
| QR стойки и отдельный QR каждого стола | да | да |
| Печать QR-флаера | да (80 мм) | нет — QR только на экране |

При изменении набора ключей раздела правки нужны в обоих клиентах:
`src/features/settings/sections/OnlineOrdersDetail.tsx` и
`backoffice/src/QrChannels.jsx` (+ `online.js`).

## Пауза приёма и время приготовления (054, Square-стиль)

На экране «Онлайн» в шапке — две кликабельные пилюли (как «Orders on» и
«20 min prep time» в Square), каждая открывает свой отдельный шит:

- **Статус приёма** (зелёная/жёлтая/серая точка) → шит «Приём заказов» с паузой на
  30 мин / 1 час / 2 часа / до конца дня. Пауза снимается сама —
  это метка `paused_until` в `locations.settings.online_orders`,
  сравнение по времени, без крона. Возобновить можно и вручную.
- **Время приготовления** → шит «Время приготовления»: диапазон min–max
  или «Не показывать».
  Гость видит вилку времени, а после принятия — обратный отсчёт до верхней
  границы.

Пишут точечные RPC `set_online_pause` / `set_online_prep_range`
(миграции 054/061) — не `update_location_config`: тот требует `manage`,
а паузу должен уметь ставить и бариста. Право — `online_pause`
(ANGLE → Team → Permissions), по умолчанию доступно всем.

`set_online_prep_minutes` оставлен как обратимо совместимая обёртка
`min=max`. Старый ключ `prep_minutes` также читается как диапазон из одного
значения.

Enforcement: `submit_online_order` отклоняет заявку кодом `paused`;
`public-menu` отдаёт `accepting` с учётом паузы + `paused_until`
(гость видит «приём приостановлен до 14:30») и `prep_min`/`prep_max`.
Порядок деплоя тот же: миграция → edge function `public-menu` → фронтенд.

## Типы заказа: здесь / с собой / доставка (058)

Гость выбирает тип заказа при оформлении; владелец включает варианты в
ANGLE → QR menu → Online orders → «Order types» (тумблеры
здесь/с собой/доставка, хотя бы один обязателен). Хранится в
`locations.settings.online_orders.order_types` (массив). Отсутствие/пусто
= дефолт `['here','takeaway']` — старые точки без настройки продолжают
работать (раньше был хардкод `takeaway`).

- `public-menu` отдаёт `location.order_types`; гостевая страница
  показывает вопрос «Как хотите получить?» только если включён >1 типа
  (один — не спрашиваем). Доставка требует адрес (поле на чекауте).
- `public-order` прокидывает `order_type`/`delivery_address` в
  `submit_online_order` — тип валидируется по списку владельца
  (`invalid_order_type`), адрес обязателен для доставки
  (`invalid_address`). Хранятся в `online_orders.order_type` /
  `.delivery_address`.
- `accept_online_order` передаёт сохранённый тип в `place_order` (не
  хардкод) и копирует адрес в `orders.delivery_address`. Тип заказа и
  адрес видны кассиру на карточке заявки (`/online`).

**Порядок деплоя (как всегда):** миграция 058 → `public-menu` +
`public-order` → фронтенд.

## Плитки категорий на главном экране гостя (080)

Главный экран онлайн-меню — сетка плиток категорий (стиль Wolt). Обложка
плитки берётся так:

- **своя обложка категории** `menu_categories.cover_url`, если задана;
- иначе **фото первого товара** категории (прежнее поведение).

Владелец ставит обложку в Меню → Товары → строка категории → иконка
«картинка» (поповер): загрузить своё фото (бакет `menu-images`, как фото
товара), выбрать фото одного из товаров категории или «Сбросить на авто».
`public-menu` отдаёт `categories[].cover_url`; `PublicOrderPage` берёт
`cover_url ?? фото первого товара`.

Обрезка обложки на плитке: горизонтальные фото заполняют карточку
(`object-cover`), вертикальные (стакан, бутылка) в cover-кропе теряют верх
и низ — такие `CategoryCover` показывает целиком (`object-contain`) на
белом фоне (фото меню студийные на белом, подложка сливается со снимком).

**Порядок деплоя:** миграция 080 (`ALTER TABLE menu_categories ADD COLUMN
cover_url`) → `public-menu` → фронтенд. Старый клиент колонку не читает —
совместимость сохраняется.
