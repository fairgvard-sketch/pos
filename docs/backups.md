# Бэкапы и восстановление

Production хранит финансовую историю заведений — резервное копирование это
условие эксплуатации, а не опция. Требование квартальной копии и контроля
восстановления входит и в регуляторные обязательства
([israel-compliance.md](israel-compliance.md), «Резервные копии»).

Инструкция сверена 13.09.2026. F5 общего
[плана](../../anglesite/docs/product-completion-plan.md) закрыт в части
локального restore: копия схемы 167 восстановлена и обновлена до 168.
Это не подтверждение полной готовности production к аварии.

## Согласованные требования и текущий разрыв

Владелец согласовал **RPO ≤15 минут** (допустимая потеря данных) и
**RTO ≤1 часа** (возобновление работы). Эти цели пока не обеспечены.
В Dashboard проекта `qgmnxrgtlpyqglwqmsej` 13.09.2026 подтверждены Free Plan,
отсутствие managed scheduled backups и недоступность PITR без платного
плана/add-on. Платные настройки не включались. Ограничения сервиса — в
[документации Supabase](https://supabase.com/docs/guides/platform/backups).

Требуется решение владельца: PITR либо отдельно спроектированное автоматическое
резервирование с внешней зашифрованной копией, контролем возраста/ошибок и
проверкой восстановления. Копия файлов Storage и полный сервисный drill
остаются обязательными. Суточный дамп не закрывает RPO 15 минут; даже запуск
каждые 15 минут сам по себе не гарантирует его — учитывать время выгрузки,
сбои и возраст последней успешной **внешней** копии.

## Слои защиты

| Слой | RPO | Кто включает / выполняет |
|---|---|---|
| PITR (WAL-архивация) | минуты | владелец: Dashboard → Database → Backups → Point in Time; **основной механизм**, суточный бэкап теряет до дня продаж |
| Ежедневные managed-бэкапы | до суток | входят в платный план; наличие и срок хранения проверять в Dashboard → Database → Backups |
| Логический дамп `npm run db:dump` | на момент дампа | вручную: перед крупными миграциями и раз в квартал (квартальную копию — вне машины разработчика, зашифрованной) |
| Файлы Storage (фото меню, логотипы) | — | в pg-дамп **не входят**; см. «Storage» ниже |

## Логический дамп

```bash
npm run db:dump   # guard → backups/<UTC timestamp>-<random>/
```

Что внутри `data.sql`: схемы `auth` (устройства-аккаунты с паролями), `public`
(все доменные данные, включая счётчики и `setval` для sequences) и метаданные
`storage`. Дамп содержит PIN-хэши сотрудников и телефоны гостей — хранить
только зашифрованным, каталог `backups/` в `.gitignore`.

[Скрипт](../scripts/db-dump.mjs) создаёт уникальный каталог каждого запуска,
не перезаписывая предыдущую копию. Каталог 0700, файлы 0600; символическая
ссылка вместо `backups` запрещена. После успешных команд, проверки непустых
файлов и footer data-дампа последним записывается `manifest.json` с размерами
и SHA-256. Supabase удаляет footer из schema-дампа, а роли могут состоять
только из комментариев: их полноту footer не доказывает.

При отказе команда завершается с ошибкой, частичный приватный каталог остаётся
**без manifest**, чувствительный stderr не печатается. Manifest не доказывает
restore, шифрование или offsite (`restoreTested: false`,
`storageObjectsIncluded: false`). Старые копии без manifest проверять отдельно,
не дописывать им подтверждение задним числом. Права 0600 не заменяют шифрование.

Не менять схему между тремя командами дампа: они не используют единый общий
snapshot. Версию БД, ревизию миграций и время фиксировать в закрытом журнале.
Не передавать дамп в CI/Claude/чат. Контролировать место на диске: автоматическое
удаление старых копий не реализовано. Безопасные тесты обёртки без Supabase:
`npm run test:ops`.

## Восстановление

Сначала определить точный проект, момент восстановления и допустимую потерю
данных; получить согласование владельца перед восстановлением production.
Учебный прогон выполнять в новой изолированной БД без внешней сети,
опубликованных портов и тома с исходными данными. Не делать `supabase db reset`
над существующим локальным стеком с данными. Привязка CLI к новому проекту сама
по себе не меняет `EXPECTED` в project-ref guard: не обходить его молча.
Для аварийной смены проекта нужен отдельный проверенный план переноса
конфигурации, Auth, секретов, Storage и клиентов. Старый прогон ниже не
заменяет испытание этого плана на актуальной схеме.

### Сценарий А: порча/потеря данных, проект жив → PITR

1. Dashboard → Database → Backups → Point in Time → выбрать момент **до**
   инцидента. Восстановление откатывает весь проект целиком: заказы, пробитые
   после точки восстановления, будут потеряны — их пере-проводят по бумажным
   чекам компенсирующими операциями, а не повторным restore.
2. После восстановления обязательно: блок «Верификация» ниже, сверка последнего
   `receipt_number` с последним физически напечатанным чеком, полный
   [smoke-test T2](t2-smoke-test.md).

### Сценарий B: учебный restore, затем план переноса сервиса

1. Зафиксировать хеши исходной копии, версию схемы и перечень COPY-таблиц.
   Исходные файлы не изменять. Пароли не передавать в argv или открытые логи.
2. Поднять чистый совместимый Supabase/Postgres. Ранний init образа Postgres
   может не содержать актуальных колонок Auth/Storage: согласовать технические
   схемы до загрузки данных. При schema-only переносе исключить прикладные
   Storage-политики, ссылающиеся на ещё отсутствующие public helpers — их
   создают миграции.
3. Применить канонические миграции **до версии дампа**, с ledger. Не включать
   копии файлов с суффиксом ` 2`. `schema.sql` — резерв, не второй набор DDL
   поверх миграций. Custom roles разобрать отдельно; не игнорировать ошибки
   общим «already exists допустимо». В принятой копии custom roles не было.
4. Убедиться, что target — именно новая тестовая БД. Миграции создают seeds
   (`product_catalog`, capabilities/prices, `reserved_slugs`, billing settings):
   простой COPY поверх них конфликтует. Только в подтверждённом restore-target
   очистить точный набор восстанавливаемых auth/public таблиц и загрузить
   проверенные COPY-блоки **одной транзакцией** с
   `SET LOCAL session_replication_role = replica`. Иначе складские триггеры
   проведут списания повторно. Не использовать общий CASCADE или произвольный
   SQL вне проверенных COPY/sequence-команд. `storage.*` не заливать поверх
   управляемой сервисом схемы; файлы восстанавливаются отдельно.
5. Перенести **все** sequences вместе с `is_called`, включая самостоятельные
   счётчики, не только serial. После COMMIT проверить режим триггеров `origin`.
   Важно: `setval` не откатывается транзакцией
   ([PostgreSQL](https://www.postgresql.org/docs/17/functions-sequence.html)).
   После ошибки на этапе sequences считать target непригодным и повторять
   restore в новой изолированной БД; не обещать полный rollback всего состояния.
6. Сверить все таблицы по количествам и хешам отсортированных COPY-строк при
   одинаковом порядке колонок, UTC и формате дат. Проверить FK заново: режим
   replica отключает и их триггеры. Выполнить финансовую проверку ниже.
7. Применить последующие миграции и повторить сверку с учётом ожидаемых
   backfill. В прогоне 167 → 168 данные не изменились. Отдельно испытать
   отказ во время COPY до sequences: ненулевой exit и rollback всех таблиц.
8. После приёмки удалить только временную копию, исходные бэкапы сохранить.

Это ещё не возврат сервиса после потери проекта. Для него нужны согласованный
новый проект, Auth/JWT и SMTP, Edge Functions и Secrets, buckets/policies и
файлы, frontend env/DNS, смена project-ref guard и повторный вход устройств.
Не обходить guard молча. В дампе нет конфигурации всех этих сервисов. Проверить
с обычным владельцем вход, права, заказ и [печать T2](t2-smoke-test.md).
RTO измерять от инцидента до возобновления работы, а не по времени COPY.

### Верификация после восстановления

```bash
# Заранее настроенный libpq service ИЗОЛИРОВАННОЙ тестовой БД, не production.
# Пароль не передавать в командной строке.
psql "service=$RESTORE_TEST_SERVICE" -X -v ON_ERROR_STOP=1 -v VERBOSITY=sqlstate \
  -f scripts/verify-restored-data.sql
```

[Верификатор](../scripts/verify-restored-data.sql) проверяет данные во временных
таблицах и делает ROLLBACK; постоянных изменений нет, при расхождении exit
ненулевой. Учитываются выданные чеки, `fulfilled`, чаевые, отрицательные
refund-платежи, непрерывность чеков/возвратов **по каждой точке**, closed shifts,
FK и различающийся `org_id` у связанных записей. Это не полный RLS-аудит и не
сравнение с дампом: хеши всех таблиц, sequences и ожидаемую версию схемы
проверять дополнительно. Строки, PIN/пароли и данные гостей не публиковать.

### Storage

SQL-копия и DB PITR не содержат байты фотографий/логотипов. Для внешней копии
нужны файлы, их пути, bucket-конфигурация и контрольные суммы. При смене
проекта абсолютные URL в каталоге указывают на старый домен: предусмотреть
проверенный перенос ссылок. Ручная перезагрузка допустима только при согласии
владельца на соответствующую потерю/простой.

HEAD 200 доказывает лишь доступность объекта сейчас, не его копирование.
Проверять только согласованные объекты и хост, без передачи токенов и дампа.

## Регламент

- **Квартально**: `npm run db:dump` → зашифрованная копия вне машины
  разработчика → строка в журнал ниже.
- **Перед рискованными релизами и по согласованному расписанию**: сценарий B
  в новой изолированной БД; существующий локальный стек не сбрасывать.
- **Перед крупными миграциями** (денежные таблицы, массовый backfill):
  свежий `npm run db:dump`.
- До закрытия F5: автоматическая внешняя защита под RPO, владелец оповещений,
  тест отказа задания/просроченной копии и полный сервисный drill под RTO.
