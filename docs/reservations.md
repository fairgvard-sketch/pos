# Бронирование столов с сайта (053–063)

Гость бронирует стол на публичной странице. В обычном режиме касса подтверждает
заявку; в instant-режиме сервер проверяет доступность и подтверждает бронь сразу.
Система построена по образцу онлайн-заказов: staging-таблица, Edge Function под
service_role, realtime-уведомление в сайдбаре и настройки на уровне точки.

## Поток

```
Гость /reserve/<location_id>
  → форма: дата, время, гости (лимит задаёт точка), имя, телефон, комментарий
  → POST public-reserve {action:'submit'} → submit_reservation (service_role)
  → заявка в reservations (status='new'), client_uuid — секрет гостя
Касса (сайдбар, режим столов)
  → realtime: звонок playReservationChime + тост + бейдж «Брони»
  → /reservations: Подтвердить (опционально сразу стол) / Отклонить (причина)
Гость (поллинг 5с по client_uuid)
  → confirmed: «Бронь подтверждена» (+ стол) | rejected: причина
  → может отменить бронь (cancel) — касса получит тост «Гость отменил»
Instant-режим
  → GET live-доступности → submit_reservation сам подбирает стол
  → confirmed без ручного действия кассы | full_slot при гонке
План зала /hall
  → стол с confirmed-бронью в окне [now−30мин, now+2ч] — синий + время
    (вычисляется на клиенте, tables.status не трогаем)
```

## Ключевые решения

- **Тумблер default = ВЫКЛЮЧЕНО** (`locations.settings->reservations->enabled`,
  отсутствие ключа = выкл — в отличие от online_orders). Включается:
  ANGLE → QR menu → Reservations (со 107 настройки канала живут
  только в бэкофисе). Enforced на сервере
  (`submit_reservation` → код `disabled`; организация без capability
  `public_reservations` отклоняется раньше кодом `module_disabled`, тот же
  гейт стоит на `reservation_availability` и `get_reservation_status`,
  веб-стол — `reservations_desk` (105) — см. «Продукты, capabilities и
  entitlements» в `database.md`). Тумблер не заменяет entitlement.
- **Открытая смена не нужна** ни для заявки, ни для подтверждения — бронь
  обычно на будущую дату. Вместо «часов приёма» окно времени:
  `NOW()+30 мин … NOW()+30 дней` (код `invalid_time`).
- **Статусы только вперёд**: `new → confirmed | rejected | cancelled`;
  `confirmed → rejected` (касса отменяет по звонку гостя) и
  `confirmed → cancelled` (гость сам). Статуса `expired` нет — прошедшие
  скрывает клиент фильтром по `reserved_at` (визит был >2ч назад → история).
  Прошлые дни доступны на вкладке «История» (113): отдельный запрос за
  период (сегодня / 7 / 30 дней) с поиском по имени и телефону — активный
  экран остаётся коротким и грузит только сегодня и будущее.
- **Стол опционален**: назначается при подтверждении (пикер с подсказкой о
  конфликте ±2ч — не блокировка) или позже (`set_reservation_table`).
- **Анти-спам** в `submit_reservation`: ≤3 заявок с телефона за 15 мин
  (`rate_limited`), ≤30 необработанных на точку (`busy`).
- Идемпотентность: `client_uuid` UNIQUE, повторный POST → `duplicate:true`.
- Гостю наружу уходит только `settings->reservations` (флаг), не весь settings.

## Веб-стол хостес без POS (102)

Standalone-модуль ANGLE Reserve: полный цикл брони ведётся из кабинета
(`anglesite`, раздел Reservations) без устройства и PIN.

- `set_reservation_status_web(location, id, status, reason)` — переводы:
  `new → confirmed|rejected|cancelled`, `confirmed → cancelled|completed|
  no_show`. Только owner/manager-членство (091/096), модуль
  `reservations` обязателен; атрибуция — `decided_by_member`.
- Статусы `completed`/`no_show` — терминальные и **сознательно вне
  предикатов движка доступности** (occupancy, exclusion-индекс 063
  считают занятость по `new`/`confirmed`): визит занимает стол в
  `confirmed`, терминальный статус освобождает окно. Активные
  arrived/seated в v1 не добавлялись — это переделка движка.
- Брони, посаженные в POS-заказ (`order_id`, `seat_reservation` 057),
  из веба неприкасаемы (`pos_mode`) — «посадить и открыть заказ»
  остаётся возможностью точек с POS.
- Гостевая страница: `no_show` показывается как отмена, `completed` —
  подтверждённая карточка без кнопки отмены.

pgTAP: `reservations_web_desk.test.sql`.

## Мгновенная бронь + вместимость (063, «Ontopo»)

Платформенная надстройка: гость видит **live-доступность** и бронь
подтверждается **мгновенно** без хостес (как Ontopo). Всё за флагами
`settings.reservations`, дефолты консервативны — каждое кафе включает нужное.

### Что добавилось

| Слой | Изменения |
|------|-----------|
| Миграция `063_reservation_availability.sql` | `tables.seats`/`combinable`; поля брони `duration_min`/`auto`/`hold_table_ids`/`deposit_*`/`occupancy`; EXCLUDE `reservations_no_overlap`; RPC `reservation_availability`, `guest_history`, `_pick_tables`/`_table_free`; `submit_reservation`/`accept_reservation` v2 |
| Edge `public-reserve` | GET `?loc&date&party` → сетка `{time,free}`; info отдаёт `instant`; ошибка `full_slot` |
| Гость `PublicReservePage` | занятые слоты дизейбл/зачёркнуты, «Забронировать сейчас», мгновенное подтверждение |
| Касса `TableEditSheet` | поле «мест» + тумблер «можно объединять» |
| Касса `ReservationsPage` | CRM-бейдж гостя (постоянный/отмены) + бейдж «Авто» |
| ANGLE `QrChannels.jsx` → `ReserveTab` | тумблеры instant/combine, длительность/буфер, депозит |

### Модель доступности

`reservation_availability` идёт по слотам дня [open..close] шага slot_min и для
каждого зовёт `_pick_tables`: наименьший свободный стол с `seats>=party`, а при
`combine=true` — жадно набирает `combinable`-столы до суммарной вместимости.
Свободен = нет живой (new/confirmed) брони, чьё окно занятости
`[reserved_at, +duration_min)` (± `buffer_min`) пересекает слот. Гонку двух
инстант-гостей на один стол ловит EXCLUDE-констрейнт → `full_slot`.

### Флаги `settings.reservations` (все опциональны)

`instant` (мгновенное подтверждение, деф off) · `combine` (объединение столов) ·
`duration_min` (деф 90) · `buffer_min` (деф 0) · `deposit_required`/
`deposit_amount`(агороты)/`deposit_from_party` (ПЛЕЙСХОЛДЕР, без оплаты;
со 117 переключатель убран из кабинета — оплаты за ним нет).

Со 117 `open`/`close` — **устаревшая пара**: часы задаются недельным
расписанием `schedule` (следующий раздел). Пара сохранена как фолбэк и
читается, только пока у точки нет `schedule`.

## Бронь по зонам (072)

Если у точки две и больше живых зон зала (066) с активными столами, гость на
шаге «точное время» видит их **секциями в стиле Ontopo**: у каждой зоны свой
заголовок и ряд слотов (±2 вокруг запрошенного времени). Тап по слоту в секции
означает бронь этой зоны на это время. Одна зона (066 создаёт всем «Зал») —
единственная секция без заголовка, поведение прежнее.

- В **instant-режиме** у каждой секции своя live-доступность
  (`GET ?loc&date&party&zone=<uuid>`, по запросу на зону через `useQueries`):
  свободный слот подписан «мгновенно» с зелёной точкой, занятый — ⊘ и
  недоступен. В обычном режиме все слоты — «по телефону» (⊘ не показывается,
  доступность не запрашивается).
- Зона — **пожелание гостя**, хранится в `reservations.zone_id`
  (составной FK `reservations_zone_fk` → `table_zones` в скоупе точки).
  Зоны не удаляются физически (`delete_table_zone` — soft), поэтому имя
  резолвится по id без снапшота.
- В **обычном режиме** касса видит пожелание бейджем на карточке брони и в
  шапке пикера стола (столы там уже сгруппированы по зонам) — ограничения нет.
- В **instant-режиме** `_pick_tables` подбирает стол только в выбранной зоне;
  зона занята целиком на слот → `full_slot`.
- `submit_reservation`/`reservation_availability` валидируют зону
  (живая, этой точки) → код `invalid_zone`.
- Гость видит выбранную зону в сводке перед отправкой и в статусе брони
  (`get_reservation_status` → `zone_name`).
- Список зон наружу отдаёт `public-reserve` GET `?loc` (`zones: [{id,name}]`) —
  только живые зоны с активными столами. Имена зон гостю показываются как
  ввёл владелец: страница брони he-only, зоны стоит называть на иврите.
- Попутно исправлен баг 063: цикл слотов `reservation_availability` по TIME
  зацикливался навсегда при `close >= 23:45` (это дефолт, когда часы приёма
  не заданы) — TIME заворачивается через полночь. Итерация переведена на
  минуты. До 072 instant-режим без настроенных часов приёма вешал RPC.

Деплой как обычно: миграция `072_reservation_zones.sql` → deploy
`public-reserve` → фронтенд. Старые клиенты кассы продолжают работать: колонка
`zone_id` для них невидима, RPC-параметр опционален.

## Оформление публичной страницы

Настройки бронирования также содержат:

- своё название в шапке страницы (`reservations.display_name`) — приоритетнее
  публичного имени точки (`settings.display_name`), названия из реквизитов
  чека и имени точки; пусто = прежний fallback;
- отдельное фото-шапку с fallback на шапку онлайн-заказов, затем логотип;
- адрес и необязательные координаты для точной кнопки навигации;
- многострочный текст часов работы (поле-textarea, строка на день в формате
  «`<день> · <время>`») — на первом экране часы стоят в зоне 50/50 с кнопками
  телефона/навигации: часы слева двумя выровненными колонками (день под днём,
  время под временем; `HoursRows` бьёт строку по первому « · »), кнопки справа;
  тап по кнопке навигации открывает bottom-sheet выбора приложения — Google
  Maps или Waze (при координатах — точный пин, иначе поиск по адресу);
- ссылки Instagram, Facebook и Google Review — в подвале страницы.

Поля хранятся в `locations.settings.reservations` (JSONB), а `public-reserve`
возвращает наружу только этот allow-listed профиль. Отдельная schema migration
для новых JSON-ключей не требуется; актуальный номер последней миграции смотреть
в `supabase/migrations/`.

⚠️ Многострочный текст часов работы (`reservations.hours`) со 117 **устарел**:
часы показываются из расписания (см. ниже), редактор текста убран из кабинета.
Само поле не удалено и служит фолбэком для точек, которым расписание ещё не
заполнили.

### Гостевой UX

Публичная бронь — последовательность из трёх самостоятельных экранов:

1. брендовая обложка + дата, время и количество гостей;
2. крупные горизонтальные карточки времени по зонам;
3. сводка выбора + контакты гостя.

Экраны перекрываются на переходе и едут слева направо без промежуточного
пустого кадра. Исходящий экран сохраняет свой scrollY, новый всегда начинается
сверху. Введённые контакты живут на уровне всего сценария и не теряются, если
гость вернулся изменить время.

В instant-режиме CTA первого шага и карточки конкретной зоны заблокированы,
пока соответствующая live-доступность не загружена. Нельзя временно показывать
общую доступность как доступность зоны: это создаёт ложный свободный слот.
Ошибки имени и телефона показываются после тапа по CTA с фокусом на первом
невалидном поле; неактивная без объяснения кнопка не используется.

Это только frontend-изменение: новые JSON-ключи, миграции и деплой Edge Function
для такого UX не нужны.

## Недельное расписание, исключения и окно записи (117)

До 117 часы брони жили в **двух несвязанных местах**: пара
`settings.reservations.open`/`close` — одна на все семь дней, её проверял
сервер, — и свободный текст `settings.reservations.hours`, который видел
гость. Они расходились, и это не гипотеза: на проде страница «Булочки»
писала `שבת · סגור`, а `reservation_availability` отдавала на субботу 49
свободных слотов 08:00–20:00. При `instant=true` такие брони подтверждались
автоматически — до прихода гостя их никто не видел.

Теперь источник один — `settings.reservations.schedule`:

```json
{
  "weekly": { "0": [["08:00","20:00"]],
              "2": [["12:00","15:00"], ["18:00","23:00"]],
              "6": [] },
  "exceptions": { "2026-09-21": [], "2026-10-05": [["18:00","23:59"]] },
  "lead_min": 30,
  "horizon_days": 30
}
```

- ключ дня — `EXTRACT(DOW)` строкой, окно — `["HH:MM","HH:MM"]`, пустой
  массив = выходной, несколько окон = разрыв смен (обед и ужин);
- `["20:00","02:00"]` — смена через полночь; она принадлежит дате, в которую
  **началась**, поэтому слот «01:00» показывается в дне своей смены и несёт
  момент следующих суток;
- исключение по дате **замещает** недельное правило целиком (`[]` = закрыто);
- `lead_min`/`horizon_days` заменили зашитые «+30 минут / +30 дней»; дефолты
  те же, поэтому ненастроенная точка ведёт себя как раньше;
- формат совпадает с расписанием онлайн-заказов (101/112) — диалект один.

Отличия семантики от `online_hours_open_at`, оставленные сознательно:
границы окна **включительны** с обеих сторон (059 всегда проверял
`v_local > v_close`, а цикл слотов шёл `<= to` — иначе у всех точек молча
пропал бы последний слот), и ночная дуга принадлежит только дате начала.

### Единый предикат

`reservation_bookable_at(settings, tz, at)` — **единственное** место, где
решается «попадает ли момент в часы». Его спрашивают и сетка
(`reservation_availability`), и приём заявки (`submit_reservation`), поэтому
показанное и принимаемое разойтись не могут. Вспомогательные:
`reservation_schedule(settings)` (нормализация + разворот legacy `open/close`
в семь одинаковых дней) и `reservation_day_windows(schedule, date)`.

Ручная бронь на кассе (`create_reservation`, 060) расписание по-прежнему
**не проверяет**: сотрудник вправе принять заказ на любое время (частное
мероприятие, звонок постоянного гостя). Расписание ограничивает гостя, а не
хостес.

### Часовой пояс точки на клиенте

Гостевая страница считала сетку в часовом поясе **устройства**: гость с
телефоном в другой зоне видел одно время, а бронировал другое. Со 117
`public-reserve` отдаёт `schedule` и `timezone`, а
`src/features/reservations/schedule.ts` строит ту же сетку в зоне точки —
это построчное зеркало SQL, покрытое `schedule.test.ts`. Слот несёт
абсолютный момент (`at`), он же уходит на сервер: собирать время как
«дата + метка» нельзя ни у ночной смены, ни в день перевода часов.

Весной локального 02:00 не существует, и Postgres отображает 02:00 и 03:00
в один момент — такие слоты выбрасываются из сетки на обеих сторонах, иначе
гость выбирает 02:00, а бронируется 03:00.

### Объединённые столы наконец занимают места

Тесты 117 вскрыли дефект 063: занятость считалась только по `table_id`, а
дополнительные столы объединения лежат в `hold_table_ids`. Бронь «2+4 на
шестерых» держала один стол, второй оставался свободным — две компании
садились за один стол без единой ошибки. `_table_free` расширена на массив.
Остаточный риск: EXCLUDE-констрейнт по-прежнему покрывает только `table_id`,
поэтому гонка двух **одновременных** объединённых броней на общий стол
возможна; закрытие требует явной связи «бронь ↔ столы» (Phase 3).

### Редактор

ANGLE → QR menu → Reservations → «Booking hours»: окна по дням недели с
кнопкой «добавить смену», исключения по датам, запас до визита и горизонт
записи, предпросмотр ближайших семи дней. Свободный текст часов из кабинета
убран — иначе второй источник истины вернулся бы.

### Бэкфилл и откат

Миграция forward-only и ничего не удаляет. Расписание заполняется **разбором
текста `hours`** (решение владельца: именно этот текст описывал реальный
график); точка, чей текст не разобран или покрывает не все семь дней,
получает расписание из `open`/`close` и попадает в `NOTICE` — такие точки
надо проверить в кабинете глазами. Функциональный откат одной точки:

```sql
UPDATE locations SET settings = settings #- '{reservations,schedule}'
WHERE id = '<location_id>';
```

После этого снова действует legacy-пара `open`/`close`.

Инварианты: `supabase/tests/reservation_schedule.test.sql` (42 проверки —
закрытый день, разрыв смен, исключения, полночь, DST, буфер, объединение,
выключенные столы, EXCLUDE-гонка, совместимость) и
`src/features/reservations/schedule.test.ts` (25 проверок).

## Самообслуживание гостя: ссылка, перенос, отмена (118)

Доступ гостя к собственной брони держался на `client_uuid` в localStorage
ТОГО браузера, где её оформили: сменил телефон, почистил данные, открыл
ссылку в другом приложении — брони для гостя больше нет, и восстановить её
продукт не умел. Перенести время было нельзя вовсе: только отменить и
оформить заново, потеряв стол. Каждый такой случай — звонок в заведение.

### Постоянная ссылка

`reservations.public_token` — серверный секрет ссылки. Отдельно от
`client_uuid` сознательно: тот генерирует браузер и он же ключ
идемпотентности POST, а стойкость долгоживущего URL нельзя доверять чужому
ГПСЧ. Токен возвращает `submit_reservation`, страница кладёт его в адрес
(`/reserve/<loc>?b=<token>`, `history.replaceState`) и в localStorage.
Открывается бронь по любому из двух ключей — старые ссылки продолжают
работать.

### Что можно гостю — решает сервер

`reservation_public_view(key)` отдаёт карточку брони (статус, визит, зона,
стол, адрес/телефон/координаты точки, текст правил) и главное — `can_cancel`
/ `can_reschedule` с кодом причины отказа. Клиент это только показывает.
Правила отсечки живут в одном месте — иначе они разойдутся, как разошлись
часы до 117.

Настройки (`settings.reservations`, обе опциональны, дефолт 0 = как раньше):
`cancel_cutoff_min`, `reschedule_cutoff_min` — за сколько минут до визита
закрывается действие. Отсечка НЕ действует на заявку в статусе `new`:
держать гостя нерешённой заявкой и одновременно запрещать её снять нельзя.
Посаженную на кассе бронь (`order_id`) веб не трогает — код `pos_mode`.

### Перенос

`reschedule_reservation(key, at, zone)` прогоняет новое время тем же путём,
что и первичную заявку: окно записи, расписание 117, живая зона, подбор
стола. Отличия по режиму:

- **instant** — сервер подбирает стол на новое время (исключая саму бронь),
  бронь остаётся подтверждённой;
- **обычный** — подтверждённая бронь возвращается в `new` и теряет стол:
  заведение подтверждало конкретное время, считать согласие на другое молча
  нельзя.

Неудачный перенос (`full_slot`, `outside_hours`, `too_late`) **не трогает
старое время** — гость не теряет бронь, пытаясь её подвинуть. Число
переносов ограничено тремя (`reschedule_limit`), иначе одна бронь
бесконечно ходит по сетке, вытесняя чужие. След переноса — в колонках
`previous_reserved_at`, `rescheduled_at`, `reschedule_count`.

### Гостевая страница

- карточка брони показывает адрес, телефон и кнопку навигации (Google
  Maps / Waze) — за «как доехать» больше не надо возвращаться на витрину;
- «добавить в календарь» отдаёт `.ics`, собранный на клиенте
  (`calendar.ts`). Событие пишется в UTC, поэтому VTIMEZONE не нужен и
  перевод часов не искажает момент;
- перенос идёт через тот же движок сетки, что и первичный выбор времени —
  гость не встречает вторую, непохожую логику;
- конфликт на отправке (`full_slot`) возвращает гостя к выбору времени со
  СВЕЖЕЙ доступностью и объяснением; контакты не стираются;
- поллинг статуса теперь только для заявок в статусе `new`; решённая бронь
  сама по себе не меняется, и опрашивать её каждые 5 секунд незачем.

### Метаданные и установка

`/reserve/*` получил свой web-manifest (`surface=reserve` в
`buildMenuManifest`, `scope: '/reserve/'`) — до этого установленная «бронь»
открывалась на витрине меню. Заголовок вкладки и имя устанавливаемого
приложения берут название заведения вместо родового «Angle — Digital Menu»,
у гостевой сборки появились `description` и og-теги.

Язык страницы остаётся ивритом (`he`-only, как печатные документы).
Английская и русская витрина не вводились: `Lang` в `src/lib/i18n.ts`
поддерживает ровно `ru | he`, и третий язык — это отдельная работа по
всему словарю, а не пункт этой фазы.

Инварианты: `supabase/tests/reservation_self_service.test.sql` (30 проверок)
и `src/features/reservations/calendar.test.ts` (12 проверок).

## Таймлайн хостес (119)

Экран броней в кассе открывается **таймлайном**: столы по вертикали,
время по горизонтали, визит — блок длиной в длительность. Список карточек
остался вторым видом (переключатель «Таймлайн / Список») — по нему удобнее
решать заявки и искать по имени, а вкладка «История» не изменилась.

Что показывает полотно: часовая шкала и метка «сейчас», зоны зала
секциями с фильтром, состояние визита цветом И текстом (ждёт решения /
подтверждена / за столом / ушли / не пришли), объединённые столы — одним
блоком на каждой строке, выключенные столы — серой полосой, пересечения
живых броней — красной обводкой. В шапке сводка, ради которой хостес
смотрит на экран первые пять секунд: занято столов, свободно мест,
придут в ближайший час, ждут решения.

Тап по блоку открывает действия: подтвердить заявку, назначить или
сменить столы, «гость сел», посадить в POS-заказ (только там, где есть
касса), отклонить.

Геометрия вынесена в чистый модуль `src/features/reservations/timeline.ts`
и покрыта тестами (`timeline.test.ts`, 22 проверки, включая объём
50 столов × 200 броней). Компонент только рисует посчитанное: «блок налез
на соседний» должно падать в тестах, а не обнаруживаться в час пик.

### Связь брони со столами

`reservation_tables` — одна строка на стол визита, включая добавленные
объединением. Ведётся ТРИГГЕРОМ из `reservations` (table_id +
hold_table_ids + occupancy + status), поэтому шесть RPC, пишущих бронь,
переписывать не пришлось и забыть про связь негде.

На этой таблице висит `EXCLUDE (table_id =, occupancy &&) WHERE is_live` —
и он закрывает то, что 117 закрыть не могла: **гонку двух одновременных
объединённых броней**. Раньше занятость считалась по `table_id`, а
дополнительные столы лежали в массиве, который gist-исключением не
покрыть. `_table_free` теперь читает один индексируемый предикат отсюда же.

Терминальный статус (`completed`/`no_show`) снимает `is_live` — стол
освобождается, но строка остаётся: таймлайн показывает и прошедшие визиты.

### Посадка гостя

`reservations.arrived_at` — момент, когда гость сел. Отдельного статуса
сознательно нет: POS уже отмечает посадку наличием `order_id` (057), и
второй способ выражать то же состояние разошёлся бы с первым. Флаг ставят
оба контура — касса при `seat_reservation`, хостес через
`mark_reservation_arrived`. Для точки **без POS** это и есть посадка:
счёт не открывается, стол занят до завершения визита.

### Действия хостес

| RPC | Что делает |
|---|---|
| `set_reservation_tables(id, staff, table_ids[])` | назначить / объединить / разъединить одним вызовом; первый стол становится основным, конфликт — дружелюбный `table_busy` |
| `update_reservation(id, staff, at?, party?, note?, zone?, duration?)` | правка визита; занятость перепроверяется, часы работы — нет |
| `mark_reservation_arrived(id, staff?)` | отметка посадки, идемпотентная |
| `create_reservation` v2 | потолок гостей поднят с 20 до 200 (банкет), добавлены зона и длительность, занятость стола проверяется |

Вместимость при ручном назначении **не проверяется**: хостес видит зал и
вправе посадить шестерых за стол на четверых. Часы работы для ручной брони
тоже не enforced (правило 060 сохранено) — расписание ограничивает гостя,
а не сотрудника.

Инварианты: `supabase/tests/reservation_tables_link.test.sql` (30 проверок).

### Таймлайн в кабинете (120)

Тот же таймлайн есть в ANGLE → Reservations (переключатель «Timeline /
List»), поэтому standalone-точка без кассы получает полотно наравне с
POS-точкой. Раскладка портирована в `backoffice/src/timeline.js`;
**эталон — `src/features/reservations/timeline.ts` в кассе**, где лежат её
тесты. Дублируется только геометрия: «кто какие столы занимает» приходит
из `reservation_tables`, то есть из одной таблицы для обоих контуров.

Действия из кабинета идут через веб-зеркала (120):
`set_reservation_tables_web`, `mark_reservation_arrived_web`,
`update_reservation_web`. Право даёт членство в `organization_members`,
точка приходит параметром (в JWT веб-владельца `location_id` нет), сверху
capability-гейт `reservations_desk`. Правила те же, что у кассовых RPC 119
— меняется только способ авторизации. Бронь, посаженная в POS-заказ,
из веба неприкасаема (`pos_mode`, правило 102).

### Чего в этой фазе нет

- перетаскивания блоков мышью: пересадка идёт через пикер столов;
- отдельной мобильной раскладки — полотно прокручивается горизонтально и
  на планшете работает, но под телефон не оптимизировано.

## Единый профиль гостя (121)

Профилей гостя было **два, и они не знали друг о друге**: `guests`
(031/113–115) заполнялась продажами и онлайн-заказами, а история броней
считалась отдельным агрегатом `guest_history(phone)` прямо по таблице
`reservations`. Гость, который бронирует стол каждую неделю, в базе
клиентов не появлялся вовсе, а хостес, глядя на бронь, не видел ни
заметки бариста, ни трат, ни того, что человек дважды не пришёл.

- `reservations.guest_id` + BEFORE-триггер: профиль находится или
  заводится по нормализованному телефону тем же `upsert_guest_by_phone`
  (113), которым пользуются онлайн-заказы. Один вход — один профиль,
  `UNIQUE (org_id, phone)` не даёт дублей; бронь без телефона (walk-in)
  профиля не создаёт и базу не засоряет.
- `guests.tags` — внутренние метки (VIP, аллергия, дважды не пришёл).
  Наружу не уходят: публичный контур таблицу `guests` не читает вообще,
  а колоночного гранта на `tags` нет — правка только через
  `set_guest_profile` с правом `manage`.
- `guest_audit` — кто и когда менял имя, заметку и метки. Пишется
  **триггером**, а не телом RPC: заметку клиент правит прямым UPDATE по
  колоночному гранту 114, и аудит внутри RPC был бы обходимым, то есть
  не аудитом. Сотрудник берётся из транзакционной переменной, которую
  выставляет RPC; прямой путь оставляет аккаунт устройства.
- `guest_reservation_stats(guest_id)` — визиты, будущие брони, отмены,
  неявки, первый и последний визит, любимая зона, типичный размер
  компании, последние заметки из броней. Одна функция на два места:
  карточку клиента и стол хостес, чтобы цифры не разошлись.
- `guest_history(phone)` v2 — прежняя сигнатура и прежние ключи (клиент
  кассы не ломается), плюс `guest_id`, заметка, метки, неявки и
  предстоящие. Хостес видит контекст прямо на карточке брони.
- `get_guest_card` — тело 115 **дословно** плюс `tags` и блок
  `reservations`. Денежная часть остаётся из POS: у точки без кассы
  `orders`/`favorites` пусты, а ресторанный блок полон — standalone
  Reserve не ломается.

Инварианты: `supabase/tests/guest_crm_reservations.test.sql` (29 проверок).

⚠️ Правка заметки прямым UPDATE по-прежнему разрешена грантом 114 — это
осознанно: аудит ловит её триггером, а отзыв гранта сломал бы уже
выложенные клиенты. Перевод на RPC-only — отдельная миграция после
раскатки.

## Уведомления и лист ожидания (122)

### Провайдера доставки нет — и это видно

В проекте не настроен ни один канал: ни Resend/SendGrid/SMTP, ни функция
отправки. Поэтому 122 строит **очередь и доменные события**, а адаптер
доставки остаётся выключенным: запись уходит в статус `skipped` с
причиной `no_provider`. Имитировать отправку нельзя — заведение будет
считать, что гостя предупредили.

`notification_outbox`: тип события, канал, получатель, payload, статус,
попытки, ошибка. Идемпотентность — `dedupe_key UNIQUE`: повторная
постановка (ретрай, двойное нажатие, replay) возвращает ту же запись и
второго сообщения не создаёт. Событие «бронь подтверждена» ставит
ТРИГГЕР: подтвердить можно из кассы, из кабинета и мгновенным режимом —
во всех трёх случаях событие должно возникать одинаково.

Включение доставки, когда провайдер появится: переписать
`notification_provider_ready` (одна функция) и добавить Edge Function,
разбирающую `pending`. События и шаблоны к тому моменту уже накоплены.

SMS-канал не требует симкарты: отправка идёт через шлюз агрегатора по
HTTP API с зарегистрированным именем отправителя. Юридическую границу
«транзакционное / рекламное» сообщение определяет
[israel-compliance.md](israel-compliance.md) и внешний консультант, а не
этот документ.

### Просьба подтвердить приход

`request_reservation_confirmations(location)` ставит просьбы по броням
внутри окна `confirm_window_h` (дефолт 24 часа) и помечает
`confirm_requested_at`. Идемпотентна. Гость подтверждает со своей
постоянной страницы (`confirm_reservation_attendance`), хостес видит
`guest_confirmed_at`. **Крона нет** — соглашение 103: просрочка и
«пора напомнить» считаются в момент запроса, а не фоном, который некому
чинить ночью.

### Лист ожидания

`waitlist_entries`: дата, приемлемый диапазон времени, размер компании,
приемлемые зоны, контакты, статус. Включается отдельным тумблером
(`settings.reservations.waitlist`, деф. выкл): заведение, которое не
собирается перезванивать, не должно копить обещания.

Поток: гость не нашёл слота → встаёт в лист из публичного потока →
хостес видит подходящих под освободившееся время
(`waitlist_matches`) → отправляет предложение с ограниченным сроком
(`offer_waitlist_slot`) → гость соглашается (`accept_waitlist_offer`).

Ключевое: **предложение стол НЕ держит**. Бронь создаётся только при
согласии, и слот перепроверяется в этот момент — часы, доступность,
EXCLUDE. Иначе лист ожидания сам стал бы источником фантомной занятости.
Истёкшее или уведённое предложение возвращает запись в очередь: гость не
виноват, что не успел, и места в очереди не теряет.

Подбор проверяет не только пожелание гостя, но и реальную возможность
посадить: показать в списке того, кого посадить некуда, значит обмануть
дважды.

Инварианты: `supabase/tests/notifications_waitlist.test.sql` (28 проверок).

### Чего в фазе нет

- **никакой доставки** — ни email, ни SMS, ни мессенджеров. WhatsApp и
  Telegram остаются вне продукта по решению владельца (Telegram к тому
  же технически не может писать гостю, который не начинал диалог с ботом);
- автоматической рассылки предложений: первый релиз — подбор хостес и
  ссылка, как и предписывал план;
- панели листа ожидания на кассе: она есть только в кабинете.

## План зала из кабинета (123)

### Что было сломано

Reserve продаётся отдельно от кассы (103–107), но **завести зал умела
только касса**. Зонные RPC 066/067 читают точку из `auth_location_id()`,
которого в токене веб-владельца нет, — вызов падал на `not authenticated`;
столы заводились прямым INSERT из POS-конструктора по контексту устройства.

Организация, купившая один лишь Reserve, не могла создать **ни одного
стола**. Дальше рушилось всё подряд: пуст таймлайн хостес (119/120),
`_pick_tables` (063) никого не находит, и гость видит «мест нет» на пустой
зал. Это и был последний блокер отдельной продажи Reserve.

### Веб-зеркала

Модель та же, что у 091/102/120: право даёт членство owner/manager в
`organization_members`, точка приходит параметром, сверху capability-гейт.
Общий guard — `_floor_plan_web_member(location)`.

Гейт **шире**, чем у стола хостес: план зала нужен и Reserve
(`reservations_desk`), и кассе в режиме столов (`pos_operate`), поэтому
достаточно любой из двух возможностей.

| RPC | Делает |
|---|---|
| `create_table_zone_web` | зона + набор столов одной транзакцией, идемпотентно по `p_zone_id` |
| `rename_table_zone_web` | переименование + синхронизация текстового снимка `tables.zone` |
| `delete_table_zone_web` | мягкое удаление зоны; её столы остаются в зале «без зоны» |
| `reorder_table_zones_web` | порядок зон = позиция в массиве |
| `save_table_web` | создание и правка стола, идемпотентно по `p_id` |
| `delete_table_web` | снять стол с плана (`is_active = FALSE`) |
| `set_table_status_web` | простой стола: `free` / `reserved` / `disabled` |

Кассовый путь (066/067 + прямые UPDATE под RLS) не тронут.

### Два сознательных отличия от кассы

1. **Стол с обещанным визитом не удаляется.** Касса гасит `is_active`
   молча, и бронь остаётся привязанной к столу, которого больше нет на
   плане: строка визита просто исчезает с таймлайна. Веб-путь отказывает —
   `table_in_use` (открытый счёт) или `table_booked` (живая бронь, окно
   которой ещё не закончилось). Владелец standalone-точки правит зал сам,
   без подсказки хостес, и тихая потеря визита здесь недопустима.
2. **Дубль названия стола отклоняется** при создании и при переименовании
   (`table_exists`) — включая пакетное создание вместе с зоной, иначе
   пачка заводила бы имена, которые одиночный редактор потом откажется
   сохранять. Правку существующего стола дубль НЕ блокирует: в данных,
   заведённых кассой, повторы уже могли остаться.

### Где это в кабинете

ANGLE → Reservations → **Floor plan**, четвёртым видом рядом с таймлайном,
а не в настройках: пустой таймлайн чинится столами, и путь от проблемы к
её причине должен быть в один тап. Зона заводится сразу с набором столов
(имя, количество, вместимость, префикс) — типичный первый шаг нового
клиента; поимённая правка уже потом и по желанию.

Инварианты: `supabase/tests/floor_plan_web.test.sql` (16 проверок).

## Воронка и атрибуция канала (124)

### Чего не хватало

Про бронь было известно ровно одно — **сколько заявок пришло**. Сколько
человек открыли страницу и ушли, на каком шаге, какого времени им не
хватило и откуда они пришли, не знал никто. Владелец не мог ответить ни
на «работает ли QR на столах», ни на «стоит ли открываться в понедельник».

### Что записывается, а что нет

`reservation_funnel_events` хранит **только доврачебную часть пути**:
`page_view` → `availability` → `no_slots` → `slot_selected` →
`form_started` → `submitted` / `waitlisted`.

Терминальных статусов (подтверждена, отменена, не пришёл, завершена) здесь
**нет намеренно**: они авторитетно живут в `reservations`, и вторая копия
статуса неизбежно разошлась бы с первой — отчёт начал бы спорить сам с
собой. Отчёт соединяет воронку с бронями по `reservation_id`.

Сессия — случайный UUID вкладки в `sessionStorage`. Имя, телефон и любые
персональные данные в события не попадают.

### Дедупликация — одна строка на осмысленный шаг

Уникальный индекс по `(session_id, step, wanted_date, party_size)`.
`page_view` и `form_started` случаются раз за сессию (дата и компания там
пусты), а `availability`/`no_slots` — по разу на каждую пару «дата + число
гостей». Это и нужно отчёту: гость, перебравший пять дней и не нашедший
стол, даёт пять строк неудовлетворённого спроса, а не одну и не пятьдесят.

Шаг `no_slots` и есть «самые спрашиваемые недоступные окна» из плана —
спрос, которого заведение сегодня не видит вообще.

### Атрибуция хранится дважды, и это не дубль

- **в событии** — чтобы считать конверсию канала целиком, включая тех,
  кто до брони не дошёл; иначе канал измерялся бы только победами;
- **колонками `reservations.source` и `reservations.utm`** — чтобы отчёт
  по источникам работал после чистки событий и не зависел от того, дошло
  ли событие вообще.

Канал нормализует `normalize_reserve_source(src, utm)`. Явный `src`
сильнее `utm_source`: ссылку с QR-стола заведение печатает само, и она не
должна теряться из-за того, что гость пришёл по ней из Instagram.
Синонимы (`ig`/`insta`/`instagram`) сводятся к одному имени — иначе отчёт
разделил бы конверсию канала пополам.

В кабинете QR на странице брони кодирует `?src=qr`, а копируемая ссылка
остаётся чистой: ссылка, которую владелец вставляет куда попало, не должна
выдавать себя за печатный код.

### Очередь ожидания у стойки (137)

Лист ожидания 122 построен под гостя: заявка с публичной страницы,
серверный подбор на освободившийся слот, согласие по ссылке. Живая
очередь работает иначе, и до 137 кабинет её не поддерживал: записать
подошедшего было нечем (`submit_waitlist` — только service_role),
посадить из листа нельзя вовсе, порядок жёстко по времени записи.

Веб-зеркала по модели 123 (членство owner/manager + гейт
`reservations_desk`):

| RPC | Что делает |
|---|---|
| `add_waitlist_entry_web` | записывает подошедшего гостя; идемпотентно по `client_uuid` |
| `seat_waitlist_entry_web` | сажает из очереди: визит создаётся сразу `arrived_at`, `created_via='waitlist'` |
| `reorder_waitlist_web` | расставляет `position` 1..N — только среди ждущих |
| `set_waitlist_status_web` | «гость ушёл» и возврат в очередь; записи не удаляются |

Две новые колонки: `position` (ручной порядок; NULL — по `created_at`) и
`quoted_min` (обещанное ожидание). Обещание хранится намеренно: «мы
говорили двадцать минут» через полчаса превращается в спор, и опираться
он должен на запись, а не на память двоих.

Занятость столов при посадке решает тот же `_pick_tables`, что и для
обычной брони: сетка у соседнего ноутбука отстаёт на минуту, и этой
минуты хватает на двойную посадку. Нет места — `full_slot`, а не
посадка поверх.

### Канал привода и путь заведения — разные колонки (136)

`reservations.source` отвечает на вопрос «откуда гость узнал»: qr, table,
site, instagram, google. `reservations.created_via` — на вопрос «кто
завёл визит»:

| Значение | Кто | Функция |
|---|---|---|
| `public` | гость сам на странице брони | `submit_reservation` (118) |
| `pos` | касса, по PIN сотрудника | `create_reservation` (119) |
| `backoffice` | хостес в кабинете, включая тестовую бронь | `create_reservation_web` (127), `create_test_reservation_web` (126) |
| `waitlist` | гость согласился на предложенный слот | `accept_waitlist_offer` (122) |
| `NULL` | бронь заведена до 136 — путь не записывался | — |

Смешивать их нельзя, и до 136 это уже случалось: ручная бронь кабинета
писала `source='backoffice'`, и в отчёте каналов рядом с instagram стоял
«backoffice». С 136 кабинет заполняет путь, а канал оставляет пустым —
у телефонного звонка канала привода нет.

Историю не переписываем: у старых броней `created_via` остаётся NULL, и
кабинет показывает их как «Not recorded». Догадка задним числом («есть
`decided_by` — значит касса») превратила бы пробел в факт, на который
потом сошлётся отчёт.

### Телеметрия не имеет права уронить бронь

`track_reserve_event` **не бросает исключений ни на одном пути**:
выключенный продукт, чужая точка, неизвестный шаг, превышенный лимит —
всё это возвращает 0. Клиент отправляет шаг фоном и не ждёт ответа.
Гость не должен потерять стол из-за отчёта.

Потолки: 40 событий на сессию и 5000 на точку в час — эндпоинт публичный
и без авторизации. Чистка старше 180 дней идёт оппортунистически внутри
самого трекинга (крона нет — соглашение 103).

Инварианты: `supabase/tests/reserve_funnel.test.sql` (18 проверок),
`src/features/reservations/funnel.test.ts`.

### Чего в 124 нет

Отчёта. Данные копятся, показывать их пока негде — это следующий шаг
фазы 6: метрики, экран аналитики и сетевые фильтры по точкам.

## Отчёт по броням (125)

### Точная когорта воронки (134)

Версия 125 считала `COUNT(DISTINCT session_id)` отдельно для каждого
шага. Из-за границы периода или недоставленного фонового события поздний
шаг мог оказаться больше раннего, хотя каждая строка по отдельности была
посчитана верно.

Миграция 134 сохраняет единицу измерения — анонимную сессию вкладки — но
сначала определяет максимальный наблюдавшийся шаг каждой сессии. Основная
воронка считается как «дошёл до этого шага или дальше», поэтому все шаги
принадлежат одной когорте и монотонны. `no_slots` и `waitlisted` остаются
отдельными ветвями и не считаются выбором слота или отправленной бронью.

Ответ `reserve_analytics_web` помечает этот контракт:

- `calculation_version: 2`;
- `cohort: observed_session_max_step`.

Старое имя RPC и остальные поля ответа сохранены. Предыдущая полная
реализация закрыта от клиентских ролей под внутренним именем
`reserve_analytics_web_v1_133`; публичная SECURITY DEFINER-обёртка
заменяет только блок `funnel`. Инварианты находятся в
`supabase/tests/reserve_analytics_cohort.test.sql`.

### Две оси времени — главное, что нужно понимать

Отчёт считает по **двум разным осям**, и путать их нельзя:

| Ось | Что по ней считается | Поле |
|---|---|---|
| момент действия гостя (`created_at` брони, время события) | воронка, конверсия, каналы, средний запас до визита, режим подтверждения | `basis: event_time` / `created_at` |
| момент визита (`reserved_at`) | исходы визитов, загрузка, день недели, час, зона, точка | `basis: reserved_at` |

Иначе конверсия делила бы сессии этой недели на брони, оформленные месяц
назад **на** эту неделю, — и была бы просто неверной. Ось помечена в
каждом блоке ответа, и экран обязан её подписывать: «12 броней» по одной
оси и по другой — разные числа.

### Загрузка зала

Числитель — посадко-часы **гостей** (`party_size × duration_min`),
знаменатель — посадко-часы **зала** (сумма `tables.seats` × часы приёма из
расписания 117, функция `reservation_open_minutes`).

Не по занятым столам намеренно: стол на четверых под пару — это и есть
недозагрузка, которую владелец хочет увидеть, а не спрятать.

### Воронка считается сессиями

Один гость, трижды переспросивший даты, — один человек, а не три. Поэтому
`COUNT(DISTINCT session_id)`, а не строк. При этом в блоке «спрос, который
развернули» (`unmet`) та же сессия даёт по строке на каждую дату: это
разные неудовлетворённые запросы.

Конверсия отдаётся `null`, если вершина воронки пуста: 0/0 — это «нет
данных», а не «ноль процентов», и экран показывает «—».

### Каналы

Брони, созданные до 124, канала не имеют и попадают в `unknown`, а не в
`direct`: «не измеряли» и «пришли сами» — разные ответы, подменять первый
вторым нельзя. Канал, давший сессии и ни одной брони, из отчёта не
исчезает — иначе бесполезный канал выглядел бы отсутствующим.

### Сетевой разрез

`reserve_analytics_web(p_location_ids, p_from, p_to)` принимает **массив**
точек и **пересекает** его с точками организации вызывающего
(`_reserve_report_locations`). Чужую точку нельзя показать ни при каком
наборе параметров; пустой массив = все свои. Это и есть «network-level
filters only for users authorized across locations» из плана.

Диапазон дат — локальный для каждой точки: сеть в разных часовых поясах не
получает смещённые сутки. Потолок окна — 400 дней (отчёт синхронный).

### Где это в кабинете

ANGLE → Reservations → **Analytics**, пятым видом. Свой выбор точек (сразу
нескольких) вместо общего селекта раздела — два переключателя точки на
одном экране спорили бы друг с другом.

Инварианты: `supabase/tests/reserve_analytics.test.sql` (18 проверок).

## Запуск точки: чеклист, предпросмотр, тестовая бронь (126)

### Что было сломано

Владелец включал приём тумблером — и всё. Есть ли столы, задано ли
расписание, написаны ли правила отмены, получена ли короткая ссылка — не
проверял никто. Тумблер честно открывал гостю **страницу пустого зала**.

### Чеклист считается из данных

`reserve_launch_checklist_web(location)` возвращает шаги `tables`,
`schedule`, `policy`, `branding`, `link`, `test_booking` — каждый посчитан
из БД, а не из галочки, которую владелец ставит сам: «я настроил зал»
ничего не гарантирует, а `COUNT` столов гарантирует.

Расписание засчитывается только **явное**: legacy-пара `open`/`close` и
умолчания 117 — это «ещё не настроено», владелец их не выбирал.

`ready` **не включает сам тумблер приёма**: он и есть публикация, а не
условие для неё. Иначе чеклист требовал бы включить приём, чтобы
разрешить включить приём.

В кабинете блок стоит над таймлайном и **исчезает сам**, когда всё готово
и приём включён: чеклист нужен первую неделю, а не навсегда.

### Предпросмотр — только просмотр

`/reserve/<loc>?preview=<token>` открывает гостевую страницу **даже при
выключенном приёме**. Секрет живёт в `settings.reservations.preview_token`,
проверяет его сервер (`reserve_preview_valid`, только service_role), выдаёт
и вращает — `reserve_preview_token_web`.

Страница помечена фиксированной полосой внизу на **любом шаге**: пролистав
до формы, владелец не должен решить, что смотрит боевую страницу. Отправка
заявки заблокирована — последний шаг честно говорит, что брони не создал.

У невыложенной точки live-доступности нет (`reservation_availability`
отдаёт `disabled`), поэтому предпросмотр показывает сетку расписания.
Владелец здесь проверяет часы, зоны, брендинг и сам флоу, а не занятость —
и полоса об этом прямо говорит.

Шаги воронки (124) в предпросмотре **не пишутся**: они испортили бы
конверсию точки, которая ещё не приняла ни одного настоящего гостя.

### Тестовая бронь настоящая, но помечена

`create_test_reservation_web` ставит бронь через тот же `_pick_tables` и
тот же EXCLUDE, что и гостевой поток: она занимает стол и видна хостес.
`reservations.is_test` даёт бейдж «Test» в таймлайне и в списке заявок и
**полностью исключает её из отчёта 125**.

**Почему её создаёт кабинет, а не форма гостя.** Провести её через
`submit_reservation` значило бы протащить туда режим «правила те же, но
тумблер приёма не смотрим» — то есть переписать функцию, которая держит
расписание, идемпотентность, подбор столов и гонку инстант-броней. 120 уже
разбирала эту цену: дублировать такое тело ради одного флага нельзя.

Инварианты: `supabase/tests/reserve_launch.test.sql` (15 проверок).
