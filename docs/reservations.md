# Бронирование столов с сайта (053–063)

Гость бронирует стол на публичной странице. В обычном режиме касса подтверждает
заявку; в instant-режиме сервер проверяет доступность и подтверждает бронь сразу.
Система построена по образцу онлайн-заказов: staging-таблица, Edge Function под
service_role, realtime-уведомление в сайдбаре и настройки на уровне точки.

## Поток

```
Гость /reserve/<location_id>
  → форма: дата, время, гости (лимит задаёт точка), имя, телефон, комментарий
  → POST public-reserve {action:'submit'} → submit_reservation (service_role)
  → заявка в reservations (status='new'), client_uuid — секрет гостя
Касса (сайдбар, режим столов)
  → realtime: звонок playReservationChime + тост + бейдж «Брони»
  → /reservations: Подтвердить (опционально сразу стол) / Отклонить (причина)
Гость (поллинг 5с по client_uuid)
  → confirmed: «Бронь подтверждена» (+ стол) | rejected: причина
  → может отменить бронь (cancel) — касса получит тост «Гость отменил»
Instant-режим
  → GET live-доступности → submit_reservation сам подбирает стол
  → confirmed без ручного действия кассы | full_slot при гонке
План зала /hall
  → стол с confirmed-бронью в окне [now−30мин, now+2ч] — синий + время
    (вычисляется на клиенте, tables.status не трогаем)
```

## Ключевые решения

- **Тумблер default = ВЫКЛЮЧЕНО** (`locations.settings->reservations->enabled`,
  отсутствие ключа = выкл — в отличие от online_orders). Включается:
  ANGLE → QR menu → Reservations (со 107 настройки канала живут
  только в бэкофисе). Enforced на сервере
  (`submit_reservation` → код `disabled`; организация без capability
  `public_reservations` отклоняется раньше кодом `module_disabled`, тот же
  гейт стоит на `reservation_availability` и `get_reservation_status`,
  веб-стол — `reservations_desk` (105) — см. «Продукты, capabilities и
  entitlements» в `database.md`). Тумблер не заменяет entitlement.
- **Открытая смена не нужна** ни для заявки, ни для подтверждения — бронь
  обычно на будущую дату. Вместо «часов приёма» окно времени:
  `NOW()+30 мин … NOW()+30 дней` (код `invalid_time`).
- **Статусы только вперёд**: `new → confirmed | rejected | cancelled`;
  `confirmed → rejected` (касса отменяет по звонку гостя) и
  `confirmed → cancelled` (гость сам). Статуса `expired` нет — прошедшие
  скрывает клиент фильтром по `reserved_at` (визит был >2ч назад → история).
  Прошлые дни доступны на вкладке «История» (113): отдельный запрос за
  период (сегодня / 7 / 30 дней) с поиском по имени и телефону — активный
  экран остаётся коротким и грузит только сегодня и будущее.
- **Стол опционален**: назначается при подтверждении (пикер с подсказкой о
  конфликте ±2ч — не блокировка) или позже (`set_reservation_table`).
- **Анти-спам** в `submit_reservation`: ≤3 заявок с телефона за 15 мин
  (`rate_limited`), ≤30 необработанных на точку (`busy`).
- Идемпотентность: `client_uuid` UNIQUE, повторный POST → `duplicate:true`.
- Гостю наружу уходит только `settings->reservations` (флаг), не весь settings.

## Веб-стол хостес без POS (102)

Standalone-модуль ANGLE Reserve: полный цикл брони ведётся из кабинета
(`anglesite`, раздел Reservations) без устройства и PIN.

- `set_reservation_status_web(location, id, status, reason)` — переводы:
  `new → confirmed|rejected|cancelled`, `confirmed → cancelled|completed|
  no_show`. Только owner/manager-членство (091/096), модуль
  `reservations` обязателен; атрибуция — `decided_by_member`.
- Статусы `completed`/`no_show` — терминальные и **сознательно вне
  предикатов движка доступности** (occupancy, exclusion-индекс 063
  считают занятость по `new`/`confirmed`): визит занимает стол в
  `confirmed`, терминальный статус освобождает окно. Активные
  arrived/seated в v1 не добавлялись — это переделка движка.
- Брони, посаженные в POS-заказ (`order_id`, `seat_reservation` 057),
  из веба неприкасаемы (`pos_mode`) — «посадить и открыть заказ»
  остаётся возможностью точек с POS.
- Гостевая страница: `no_show` показывается как отмена, `completed` —
  подтверждённая карточка без кнопки отмены.

pgTAP: `reservations_web_desk.test.sql`.

## Мгновенная бронь + вместимость (063, «Ontopo»)

Платформенная надстройка: гость видит **live-доступность** и бронь
подтверждается **мгновенно** без хостес (как Ontopo). Всё за флагами
`settings.reservations`, дефолты консервативны — каждое кафе включает нужное.

### Что добавилось

| Слой | Изменения |
|------|-----------|
| Миграция `063_reservation_availability.sql` | `tables.seats`/`combinable`; поля брони `duration_min`/`auto`/`hold_table_ids`/`deposit_*`/`occupancy`; EXCLUDE `reservations_no_overlap`; RPC `reservation_availability`, `guest_history`, `_pick_tables`/`_table_free`; `submit_reservation`/`accept_reservation` v2 |
| Edge `public-reserve` | GET `?loc&date&party` → сетка `{time,free}`; info отдаёт `instant`; ошибка `full_slot` |
| Гость `PublicReservePage` | занятые слоты дизейбл/зачёркнуты, «Забронировать сейчас», мгновенное подтверждение |
| Касса `TableEditSheet` | поле «мест» + тумблер «можно объединять» |
| Касса `ReservationsPage` | CRM-бейдж гостя (постоянный/отмены) + бейдж «Авто» |
| ANGLE `QrChannels.jsx` → `ReserveTab` | тумблеры instant/combine, длительность/буфер, депозит |

### Модель доступности

`reservation_availability` идёт по слотам дня [open..close] шага slot_min и для
каждого зовёт `_pick_tables`: наименьший свободный стол с `seats>=party`, а при
`combine=true` — жадно набирает `combinable`-столы до суммарной вместимости.
Свободен = нет живой (new/confirmed) брони, чьё окно занятости
`[reserved_at, +duration_min)` (± `buffer_min`) пересекает слот. Гонку двух
инстант-гостей на один стол ловит EXCLUDE-констрейнт → `full_slot`.

### Флаги `settings.reservations` (все опциональны)

`instant` (мгновенное подтверждение, деф off) · `combine` (объединение столов) ·
`duration_min` (деф 90) · `buffer_min` (деф 0) · `deposit_required`/
`deposit_amount`(агороты)/`deposit_from_party` (ПЛЕЙСХОЛДЕР, без оплаты;
со 117 переключатель убран из кабинета — оплаты за ним нет).

Со 117 `open`/`close` — **устаревшая пара**: часы задаются недельным
расписанием `schedule` (следующий раздел). Пара сохранена как фолбэк и
читается, только пока у точки нет `schedule`.

## Бронь по зонам (072)

Если у точки две и больше живых зон зала (066) с активными столами, гость на
шаге «точное время» видит их **секциями в стиле Ontopo**: у каждой зоны свой
заголовок и ряд слотов (±2 вокруг запрошенного времени). Тап по слоту в секции
означает бронь этой зоны на это время. Одна зона (066 создаёт всем «Зал») —
единственная секция без заголовка, поведение прежнее.

- В **instant-режиме** у каждой секции своя live-доступность
  (`GET ?loc&date&party&zone=<uuid>`, по запросу на зону через `useQueries`):
  свободный слот подписан «мгновенно» с зелёной точкой, занятый — ⊘ и
  недоступен. В обычном режиме все слоты — «по телефону» (⊘ не показывается,
  доступность не запрашивается).
- Зона — **пожелание гостя**, хранится в `reservations.zone_id`
  (составной FK `reservations_zone_fk` → `table_zones` в скоупе точки).
  Зоны не удаляются физически (`delete_table_zone` — soft), поэтому имя
  резолвится по id без снапшота.
- В **обычном режиме** касса видит пожелание бейджем на карточке брони и в
  шапке пикера стола (столы там уже сгруппированы по зонам) — ограничения нет.
- В **instant-режиме** `_pick_tables` подбирает стол только в выбранной зоне;
  зона занята целиком на слот → `full_slot`.
- `submit_reservation`/`reservation_availability` валидируют зону
  (живая, этой точки) → код `invalid_zone`.
- Гость видит выбранную зону в сводке перед отправкой и в статусе брони
  (`get_reservation_status` → `zone_name`).
- Список зон наружу отдаёт `public-reserve` GET `?loc` (`zones: [{id,name}]`) —
  только живые зоны с активными столами. Имена зон гостю показываются как
  ввёл владелец: страница брони he-only, зоны стоит называть на иврите.
- Попутно исправлен баг 063: цикл слотов `reservation_availability` по TIME
  зацикливался навсегда при `close >= 23:45` (это дефолт, когда часы приёма
  не заданы) — TIME заворачивается через полночь. Итерация переведена на
  минуты. До 072 instant-режим без настроенных часов приёма вешал RPC.

Деплой как обычно: миграция `072_reservation_zones.sql` → deploy
`public-reserve` → фронтенд. Старые клиенты кассы продолжают работать: колонка
`zone_id` для них невидима, RPC-параметр опционален.

## Оформление публичной страницы

Настройки бронирования также содержат:

- своё название в шапке страницы (`reservations.display_name`) — приоритетнее
  публичного имени точки (`settings.display_name`), названия из реквизитов
  чека и имени точки; пусто = прежний fallback;
- отдельное фото-шапку с fallback на шапку онлайн-заказов, затем логотип;
- адрес и необязательные координаты для точной кнопки навигации;
- многострочный текст часов работы (поле-textarea, строка на день в формате
  «`<день> · <время>`») — на первом экране часы стоят в зоне 50/50 с кнопками
  телефона/навигации: часы слева двумя выровненными колонками (день под днём,
  время под временем; `HoursRows` бьёт строку по первому « · »), кнопки справа;
  тап по кнопке навигации открывает bottom-sheet выбора приложения — Google
  Maps или Waze (при координатах — точный пин, иначе поиск по адресу);
- ссылки Instagram, Facebook и Google Review — в подвале страницы.

Поля хранятся в `locations.settings.reservations` (JSONB), а `public-reserve`
возвращает наружу только этот allow-listed профиль. Отдельная schema migration
для новых JSON-ключей не требуется; актуальный номер последней миграции смотреть
в `supabase/migrations/`.

⚠️ Многострочный текст часов работы (`reservations.hours`) со 117 **устарел**:
часы показываются из расписания (см. ниже), редактор текста убран из кабинета.
Само поле не удалено и служит фолбэком для точек, которым расписание ещё не
заполнили.

### Гостевой UX

Публичная бронь — последовательность из трёх самостоятельных экранов:

1. брендовая обложка + дата, время и количество гостей;
2. крупные горизонтальные карточки времени по зонам;
3. сводка выбора + контакты гостя.

Экраны перекрываются на переходе и едут слева направо без промежуточного
пустого кадра. Исходящий экран сохраняет свой scrollY, новый всегда начинается
сверху. Введённые контакты живут на уровне всего сценария и не теряются, если
гость вернулся изменить время.

В instant-режиме CTA первого шага и карточки конкретной зоны заблокированы,
пока соответствующая live-доступность не загружена. Нельзя временно показывать
общую доступность как доступность зоны: это создаёт ложный свободный слот.
Ошибки имени и телефона показываются после тапа по CTA с фокусом на первом
невалидном поле; неактивная без объяснения кнопка не используется.

Это только frontend-изменение: новые JSON-ключи, миграции и деплой Edge Function
для такого UX не нужны.

## Недельное расписание, исключения и окно записи (117)

До 117 часы брони жили в **двух несвязанных местах**: пара
`settings.reservations.open`/`close` — одна на все семь дней, её проверял
сервер, — и свободный текст `settings.reservations.hours`, который видел
гость. Они расходились, и это не гипотеза: на проде страница «Булочки»
писала `שבת · סגור`, а `reservation_availability` отдавала на субботу 49
свободных слотов 08:00–20:00. При `instant=true` такие брони подтверждались
автоматически — до прихода гостя их никто не видел.

Теперь источник один — `settings.reservations.schedule`:

```json
{
  "weekly": { "0": [["08:00","20:00"]],
              "2": [["12:00","15:00"], ["18:00","23:00"]],
              "6": [] },
  "exceptions": { "2026-09-21": [], "2026-10-05": [["18:00","23:59"]] },
  "lead_min": 30,
  "horizon_days": 30
}
```

- ключ дня — `EXTRACT(DOW)` строкой, окно — `["HH:MM","HH:MM"]`, пустой
  массив = выходной, несколько окон = разрыв смен (обед и ужин);
- `["20:00","02:00"]` — смена через полночь; она принадлежит дате, в которую
  **началась**, поэтому слот «01:00» показывается в дне своей смены и несёт
  момент следующих суток;
- исключение по дате **замещает** недельное правило целиком (`[]` = закрыто);
- `lead_min`/`horizon_days` заменили зашитые «+30 минут / +30 дней»; дефолты
  те же, поэтому ненастроенная точка ведёт себя как раньше;
- формат совпадает с расписанием онлайн-заказов (101/112) — диалект один.

Отличия семантики от `online_hours_open_at`, оставленные сознательно:
границы окна **включительны** с обеих сторон (059 всегда проверял
`v_local > v_close`, а цикл слотов шёл `<= to` — иначе у всех точек молча
пропал бы последний слот), и ночная дуга принадлежит только дате начала.

### Единый предикат

`reservation_bookable_at(settings, tz, at)` — **единственное** место, где
решается «попадает ли момент в часы». Его спрашивают и сетка
(`reservation_availability`), и приём заявки (`submit_reservation`), поэтому
показанное и принимаемое разойтись не могут. Вспомогательные:
`reservation_schedule(settings)` (нормализация + разворот legacy `open/close`
в семь одинаковых дней) и `reservation_day_windows(schedule, date)`.

Ручная бронь на кассе (`create_reservation`, 060) расписание по-прежнему
**не проверяет**: сотрудник вправе принять заказ на любое время (частное
мероприятие, звонок постоянного гостя). Расписание ограничивает гостя, а не
хостес.

### Часовой пояс точки на клиенте

Гостевая страница считала сетку в часовом поясе **устройства**: гость с
телефоном в другой зоне видел одно время, а бронировал другое. Со 117
`public-reserve` отдаёт `schedule` и `timezone`, а
`src/features/reservations/schedule.ts` строит ту же сетку в зоне точки —
это построчное зеркало SQL, покрытое `schedule.test.ts`. Слот несёт
абсолютный момент (`at`), он же уходит на сервер: собирать время как
«дата + метка» нельзя ни у ночной смены, ни в день перевода часов.

Весной локального 02:00 не существует, и Postgres отображает 02:00 и 03:00
в один момент — такие слоты выбрасываются из сетки на обеих сторонах, иначе
гость выбирает 02:00, а бронируется 03:00.

### Объединённые столы наконец занимают места

Тесты 117 вскрыли дефект 063: занятость считалась только по `table_id`, а
дополнительные столы объединения лежат в `hold_table_ids`. Бронь «2+4 на
шестерых» держала один стол, второй оставался свободным — две компании
садились за один стол без единой ошибки. `_table_free` расширена на массив.
Остаточный риск: EXCLUDE-констрейнт по-прежнему покрывает только `table_id`,
поэтому гонка двух **одновременных** объединённых броней на общий стол
возможна; закрытие требует явной связи «бронь ↔ столы» (Phase 3).

### Редактор

ANGLE → QR menu → Reservations → «Booking hours»: окна по дням недели с
кнопкой «добавить смену», исключения по датам, запас до визита и горизонт
записи, предпросмотр ближайших семи дней. Свободный текст часов из кабинета
убран — иначе второй источник истины вернулся бы.

### Бэкфилл и откат

Миграция forward-only и ничего не удаляет. Расписание заполняется **разбором
текста `hours`** (решение владельца: именно этот текст описывал реальный
график); точка, чей текст не разобран или покрывает не все семь дней,
получает расписание из `open`/`close` и попадает в `NOTICE` — такие точки
надо проверить в кабинете глазами. Функциональный откат одной точки:

```sql
UPDATE locations SET settings = settings #- '{reservations,schedule}'
WHERE id = '<location_id>';
```

После этого снова действует legacy-пара `open`/`close`.

Инварианты: `supabase/tests/reservation_schedule.test.sql` (42 проверки —
закрытый день, разрыв смен, исключения, полночь, DST, буфер, объединение,
выключенные столы, EXCLUDE-гонка, совместимость) и
`src/features/reservations/schedule.test.ts` (25 проверок).

## Самообслуживание гостя: ссылка, перенос, отмена (118)

Доступ гостя к собственной брони держался на `client_uuid` в localStorage
ТОГО браузера, где её оформили: сменил телефон, почистил данные, открыл
ссылку в другом приложении — брони для гостя больше нет, и восстановить её
продукт не умел. Перенести время было нельзя вовсе: только отменить и
оформить заново, потеряв стол. Каждый такой случай — звонок в заведение.

### Постоянная ссылка

`reservations.public_token` — серверный секрет ссылки. Отдельно от
`client_uuid` сознательно: тот генерирует браузер и он же ключ
идемпотентности POST, а стойкость долгоживущего URL нельзя доверять чужому
ГПСЧ. Токен возвращает `submit_reservation`, страница кладёт его в адрес
(`/reserve/<loc>?b=<token>`, `history.replaceState`) и в localStorage.
Открывается бронь по любому из двух ключей — старые ссылки продолжают
работать.

### Что можно гостю — решает сервер

`reservation_public_view(key)` отдаёт карточку брони (статус, визит, зона,
стол, адрес/телефон/координаты точки, текст правил) и главное — `can_cancel`
/ `can_reschedule` с кодом причины отказа. Клиент это только показывает.
Правила отсечки живут в одном месте — иначе они разойдутся, как разошлись
часы до 117.

Настройки (`settings.reservations`, обе опциональны, дефолт 0 = как раньше):
`cancel_cutoff_min`, `reschedule_cutoff_min` — за сколько минут до визита
закрывается действие. Отсечка НЕ действует на заявку в статусе `new`:
держать гостя нерешённой заявкой и одновременно запрещать её снять нельзя.
Посаженную на кассе бронь (`order_id`) веб не трогает — код `pos_mode`.

### Перенос

`reschedule_reservation(key, at, zone)` прогоняет новое время тем же путём,
что и первичную заявку: окно записи, расписание 117, живая зона, подбор
стола. Отличия по режиму:

- **instant** — сервер подбирает стол на новое время (исключая саму бронь),
  бронь остаётся подтверждённой;
- **обычный** — подтверждённая бронь возвращается в `new` и теряет стол:
  заведение подтверждало конкретное время, считать согласие на другое молча
  нельзя.

Неудачный перенос (`full_slot`, `outside_hours`, `too_late`) **не трогает
старое время** — гость не теряет бронь, пытаясь её подвинуть. Число
переносов ограничено тремя (`reschedule_limit`), иначе одна бронь
бесконечно ходит по сетке, вытесняя чужие. След переноса — в колонках
`previous_reserved_at`, `rescheduled_at`, `reschedule_count`.

### Гостевая страница

- карточка брони показывает адрес, телефон и кнопку навигации (Google
  Maps / Waze) — за «как доехать» больше не надо возвращаться на витрину;
- «добавить в календарь» отдаёт `.ics`, собранный на клиенте
  (`calendar.ts`). Событие пишется в UTC, поэтому VTIMEZONE не нужен и
  перевод часов не искажает момент;
- перенос идёт через тот же движок сетки, что и первичный выбор времени —
  гость не встречает вторую, непохожую логику;
- конфликт на отправке (`full_slot`) возвращает гостя к выбору времени со
  СВЕЖЕЙ доступностью и объяснением; контакты не стираются;
- поллинг статуса теперь только для заявок в статусе `new`; решённая бронь
  сама по себе не меняется, и опрашивать её каждые 5 секунд незачем.

### Метаданные и установка

`/reserve/*` получил свой web-manifest (`surface=reserve` в
`buildMenuManifest`, `scope: '/reserve/'`) — до этого установленная «бронь»
открывалась на витрине меню. Заголовок вкладки и имя устанавливаемого
приложения берут название заведения вместо родового «Angle — Digital Menu»,
у гостевой сборки появились `description` и og-теги.

Язык страницы остаётся ивритом (`he`-only, как печатные документы).
Английская и русская витрина не вводились: `Lang` в `src/lib/i18n.ts`
поддерживает ровно `ru | he`, и третий язык — это отдельная работа по
всему словарю, а не пункт этой фазы.

Инварианты: `supabase/tests/reservation_self_service.test.sql` (30 проверок)
и `src/features/reservations/calendar.test.ts` (12 проверок).
