# Соответствие POS требованиям Израиля

Статус документа: рабочая инженерная матрица на 15 июля 2026 года, раздел
Uniform Format и API налоговой обновлены 2 ноября 2026 года.

Этот документ не является юридическим или налоговым заключением. Он переводит
официальные требования в задачи для продукта. До коммерческого запуска выводы,
типы документов, форматы печати и спорные сценарии должен письменно подтвердить
израильский `רואה חשבון` или `יועץ מס`, знакомый с регистрацией бухгалтерских
систем.

выполнены release-gates ниже и не получено требуемое регистрационное
свидетельство.

## Реализуемое правило наличных

Для обычной сделки с бизнесом:

- до `6 000 ₪` включительно можно принять всю сумму наличными;
- выше `6 000 ₪` наличными можно принять не больше меньшего из `10%` суммы
  сделки и `6 000 ₪`.

В коде все расчёты выполняются в агоротах без float. Наличная часть суммируется
по всему чеку, включая смешанную оплату и «разделить поровну». `tendered` не
считается оплатой: юридический guard использует фактически зачтённый `amount`,
а сдача хранится отдельно.

Миграция `068_israel_cash_limit.sql`:

1. делает старую реализацию `pay_order_unchecked` недоступной клиенту;
2. проверяет все части до первой финансовой записи;
3. требует точного равенства суммы платежей долгу — переплата записывается как
   `tendered/change_due`, а не как завышенный `amount`;
4. сохраняет прежнюю атомарность и идемпотентность `p_payment_uuid`.

Пока POS не умеет надёжно классифицировать туриста и хранить доказательства,
туристическое исключение намеренно не включено. Для расчёта guard используется
вся сумма к оплате с чаевыми. Обе трактовки должны быть подтверждены специалистом
до production-sign-off.

## Uniform Format 1.31

Модуль должен формировать `INI.TXT` и `BKMVDATA.TXT`, после чего архивировать
`BKMVDATA.TXT` стандартным способом сжатия. Экспорт выбирает бизнес, путь и
период; создаёт уникальный идентификатор набора; завершает каждую запись CRLF;
нумерует записи `BKMVDATA.TXT` последовательно и соблюдает фиксированные длины.

| Record | Длина | Назначение для Kassa |
|---|---:|---|
| `A100` | 95 | начало набора |
| `B100` | 317 | бухгалтерские движения |
| `B110` | 376 | справочник счетов |
| `C100` | 444 | заголовок документа |
| `D110` | 339 | строки документа |
| `D120` | 222 | детали поступления/депозита |
| `M100` | 298 | движение/справочник запасов |
| `Z900` | 110 | конец набора и контрольные значения |

Для иврита спецификация задаёт Windows logical Hebrew ISO-8859-8-i либо DOS
CP862. Буквенно-цифровые поля дополняются пробелами справа, числовые — нулями
слева. `INI.TXT` содержит ведущую запись длиной 466 и summary-записи длиной 19
для каждого типа.

Регистрационный UI должен показать и дать распечатать:

- бизнес, путь, период, дату и время формирования;
- название ПО и номер регистрационного свидетельства;
- количество записей каждого типа;
- результат формирования и контрольную распечатку по разделу 2.6/приложению 4
  спецификации.

Архитектурно экспорт следует строить server-side из неизменяемых снапшотов,
версионировать по формату и покрыть golden-file тестами. Генерация только в
браузере неприемлема: старый WebView, кодировка, объём и прерывание вкладки не
дают достаточной надёжности.

### Состояние на 2 ноября 2026

Сверка кода с таблицами спецификации (разделы 3–4, приложения 1 и 5) нашла
ошибки, из-за которых симулятор отверг бы набор. Исправлено:

- константа формата в A000/A100/Z900 — `&OF1.31&` (8 символов); раньше не
  хватало закрывающего `&`, и тест закреплял ошибку;
- числовые поля A000 1014–1016 заполняются нулями, а не пробелами;
- скидка документа (1220) и строки (1266) — со знаком «−» (разъяснение 5);
- 1219 «до скидки» — без НДС, как 1221: 1219 + 1220 = 1221 и 1221 + 1222 = 1223
  сходятся до агоры, строки D110 в сумме дают 1219, а в строке
  количество × цена + скидка = итог (остаток округления цены — скидкой строки);
- ключ клиента (1225) заполнен всегда: ח.פ покупателя либо общий ключ
  разового покупателя `WALKIN` — для документов 100–710 поле обязательно;
- возврат (330) ссылается на исходный чек полями 1256/1257 (разъяснение 6) и
  наследует его покупателя — миграция `185` отдаёт эти поля из выборки;
- у возврата (330) нет строк D120: симулятор привязывает «פרטי קבלה/הפקדה»
  только к квитанциям (320/400…) и отвергает D120 зикуя как «без заголовка»
  — правило симулятора, в тексте спецификации его нет; способ выплаты
  остаётся на печатном зикуе и в учёте смены;
- карточки клиентов B110: по одной на каждый ключ клиента документов
  (`WALKIN` — «לקוחות מזדמנים», компании — по ח.פ), группа מאזן בוחן
  `CUSTOMERS` / «לקוחות». Документ Kassa закрывается сразу (320 — счёт и
  оплата, 330 — кредит и выплата), поэтому дебет карточки = кредит = сумма
  документов, остаток на начало = 0;
- чаевые не входят в документ (033): строки D120 дают ровно итог 1223,
  излишек снимается с последних строк оплаты — трактовку подтверждает бухгалтер;
- производитель ПО (1009/1010) — владелец ANGLE из секрета `UF_VENDOR_TAX_ID`,
  а не ח.פ кафе-клиента; номер свидетельства (1006) — `99999999`, пока его нет
  (так налоговая велит в Israel Invoice API v1; v2 — ח.פ/ID производителя);
- путь набора (1012) — по разделу 2.2: `OPENFRMT\<8 цифр עוסק>.<ГГ>\<ММДДччмм>`;
- контрольный отчёт 2.6 перечисляет все 27 типов приложения 1, невыпускаемые —
  нулями;
- кодировка: герэш/гершаим/макаф — ASCII-двойниками, огласовки убираются,
  кириллица транслитерируется, а не превращается в `?`.

Проводки B100 не выгружаются: по разделу 1 это движения программы, которая
сама ведёт двойную запись, а Kassa — модуль выпуска документов (A000 1013 = 0
«לא רלוונטי»); симулятор их отсутствие принимает (нули в отчёте). B110
**обязательны** — без них симулятор ставит «לקוי» («לא הועברו רשומות מסוג
חשבון בהנהלת חשבונות (B110)»): ключ клиента документа должен вести на
карточку счёта. Раньше в этом документе было сказано обратное — это было
неверно. M100 появится вместе с работающим складом (журнал `stock_movements`
есть, раздел скрыт как неготовый).

Набор для симулятора — `npm run uf:simulator` (нужен `supabase start` и
секрет `UF_VENDOR_TAX_ID` в окружении): выдуманный бизнес «קפה לדוגמא»
(ח.פ 514000009) проводит неделю продаж и 14 возвратов настоящими функциями
кассы в транзакции, которая откатывается; набор собирается тем же кодом, что
Edge Function, проверяется `validate.ts` и кладётся в
`~/Desktop/uf-simulator/OPENFRMT/…` вместе с распечатками 2.6 и приложения 4.
Прогоны симулятора:

| Дата | Набор | Итог симулятора |
|---|---|---|
| 2.11.2026, קליטה `021120261108` | 2196 записей (Kassa 1.2.0) | «לקוי»: INI, полнота данных и итоги — «תקין»; структура — нет B110 и «D120 без соответствия»; BKMVDATA — 14 × «לא נמצאה רשומת כותרת מסמך» (поле 1300) на D120 всех зикуев |
| 2.11.2026, קליטה `021120261115` | 2185 записей (Kassa 1.2.1: D120 у 330 убраны, B110 ×3) | **«תקינה»** — все типы записей «заявлено = найдено»; отчёт сохраняется для заявки на регистрацию |

Оговорка самого симулятора: проверка частичная, не на полном наборе данных

Касса выпускает только 320 и 330; `doc_type` допускает 305/400, но их никто
не ставит — в набор для регистрации идут только реально выпускаемые типы.

## Прямая передача набора по API (дополнение №1, 3.2026)

Дополнение №1 к инструкции 1.31 (v1.0, март 2026): программа, которая обязана
формировать Единый формат, обязана **сразу после формирования передать набор
в налоговую через API**. Соблюдение — условие регистрации ПО. Разрешены
готовые сторонние посредники.

Поток (OAuth2 «User Restricted»: токен выдаётся при входе владельца бизнеса
на сайт налоговой, authorization code + client id/secret приложения):

1. `POST …/UniStructFileUploadLinksApi/v1/UploadingFile/GetUrlsForUploadingFiles`
   `{caseNumber, startPeriod, endPeriod, representorCompanyId?}` → подписанные
   ссылки Google Cloud для INI и BKMVDATA, `fileUniqueId` каждого файла и
   допустимый размер (`x-goog-content-length-range`, считается по данным
   бизнеса в налоговой).
2. Для каждого файла — `POST` на `signUrl` с заголовками из ответа (начало
   resumable upload) → `201`, адрес загрузки в `Location`.
3. `PUT` файла на этот адрес; по уточнению до 32 MB — одним запросом, больше —
   частями 32/64/128 MB; успешная часть отвечает `308`.
4. `POST …/FilesStatusApi/v1/Files/get-file-status` по `fileUniqueId` →
   `Uploaded` / `Approved` / `Rejected` с причиной.

Ответ «no requirement for a uniform structure file for this case number»
означает, что передача делается по требованию налоговой к конкретному бизнесу
и периоду, а не ежемесячно. На ноябрь 2026 открыт только sandbox (в него
принимается лишь PDF до 1 MB — механизм, а не настоящий набор), production
«будет объявлен».

Для Kassa: client secret — только в Edge Function; refresh-токен владельца —
только на сервере; кнопка «передать в налоговую» после выгрузки в кабинете
и отслеживание статуса. Не реализовано. Начинать после симулятора: передавать
имеет смысл только корректный набор.

Доступ к API (руководство OpenAPI): регистрация на сайте налоговой по
удостоверению личности (не смарт-картой) → организация на портале
разработчика + подписанные регистрационные документы → одобрение письмом →
приложение (client id/secret, redirect URI) → подписка на продукты. Для
sandbox в руководстве есть демо-пользователи. Как налоговая регистрирует
разработчика без номера бизнеса, руководство не говорит — вопрос в
ApiSupport@taxes.gov.il (02-5688444).

## Israel Invoices в 2026 году

С 1 июня 2026 года инструкция устанавливает порог `5 000 ₪` без НДС для
применимых налоговых счетов: allocation number нужен, когда документ содержит
НДС, покупатель является зарегистрированным дилером, просит номер и сумма
превышает порог. Условия должны проверяться по официальной инструкции, а не по
одному числу в frontend.

Поле `allocation_no` уже есть, но этого недостаточно. Нужны:

1. server-side запрос к Tax Authority от имени уполномоченной стороны;
2. идемпотентный ключ и журнал запроса/ответа без утечки секретов;
3. сохранение allocation number в неизменяемом документе до его выдачи;
4. согласованное поведение при timeout, отказе и недоступности сервиса;
5. тестовая и production-авторизация.

Из Israel Invoice API v2.0 (7.2024), действует вместо v1.0 (7.2023):

- для חשבונית מס זיכוי (330) номер аллокации **не** запрашивается (в v1 — да);
- запрос делается, когда у документа уже есть номер Kassa (с 2025 обязателен);
- поле номера ПО без свидетельства: в v1 — `99999999`, в v2 — ח.פ/ID
  производителя;
- скидка в API — модулем, без знака (в Едином формате — со знаком «−»);
- если налоговая задержала документ, программа обязана предложить пользователю
  четыре варианта (отмена, выпуск без номера с пометкой «אין לנכות מס תשומות
  בגין חשבונית זו», обратное начисление, слушание) и сообщить выбор сервисом
  `InvoiceDecisionApi`;
- шкала порогов в v2 (2026 — 15 000 ₪) устарела: действует инструкция 12.2025
  выше — 5 000 ₪ с 1 июня 2026.
