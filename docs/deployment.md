# Выпуск и эксплуатация

В Kassa отдельно выпускаются:

1. Supabase schema/RPC и Edge Functions;
2. POS frontend на Vercel;
3. публичная Menu / Orders / Reserve-сборка из того же репозитория;
4. Android APK для Sunmi.

Сайт и кабинет владельца выпускаются из соседнего `anglesite`. Согласование
с общей БД — [общий release checklist](../../anglesite/docs/release-checklist.md).

Изменение веб-интерфейса не требует нового APK. Изменение JS-моста, origin или
Android-конфигурации требует.

## Окружения и идентификаторы

- production Supabase project ref: `qgmnxrgtlpyqglwqmsej`;
- production frontend: `https://pos.angle.co.il`;
- публичная поверхность: `https://menu.angle.co.il`, отдельная сборка
  `npm run build:menu` / `VITE_APP_SURFACE=menu`;
- APK `app_url` должен указывать на этот стабильный origin. Только собственный
  домен: автогенерённый `*.vercel.app` отвязывается от проекта при
  пересоздании деплоя и отдаёт 404 `DEPLOYMENT_NOT_FOUND`, а касса в APK
  остаётся без фронтенда до выпуска новой сборки;
- frontend использует только Supabase anon key.

Если production URL меняется, обновите Vercel, CORS/redirect assumptions,
`android/app/src/main/res/values/strings.xml` и выпустите новый APK.

## CI

`.github/workflows/ci.yml` выполняет на push в `main`, `codex/**` и pull request:

```text
frontend: npm ci → lint → check:schema → test:run → build → bundle budget
database: local Supabase → migrations from zero → pgTAP
```

Сборка использует Node 22 и placeholder Supabase variables: она проверяет типы
и bundle, но не обращается к production DB. Отдельная database job через Docker
проверяет RLS и финансовую идемпотентность только на локальной БД.

`.github/workflows/android-apk.yml` собирает debug APK и, при ручном запуске с
секретами, подписанный release APK.

## Порядок релиза

### 1. Проверить рабочее дерево и качество

```bash
git status --short
npm ci
npm run lint
npm run check:schema
npm run test:run
npm run build
npm run check:bundle
```

При изменении гостевой поверхности отдельно проверить `npm run build:menu`:
она также пишет в `dist/`, не подменять этим артефактом POS deployment.

Если менялись SQL-инварианты, на локальной изолированной базе (reset удаляет
тестовые данные, это не production-команда):

```bash
supabase start
supabase db reset
supabase test db
```

### 2. Применить миграции

Миграции нужны раньше frontend, если новый клиент вызывает новые RPC/колонки.
Фронт сверяет `MIN_SCHEMA_VERSION` с `get_schema_version()` (081): если выложить
frontend раньше миграций, кассы покажут экран «Требуется обновление базы
данных» до тех пор, пока миграции не будут применены.

```bash
npm run check:ref
npm run db:push
```

Guard должен вывести ref `qgmnxrgtlpyqglwqmsej`. Если `.env` или linked project
не совпадает, остановитесь и исправьте привязку:

```bash
supabase link --project-ref qgmnxrgtlpyqglwqmsej
```

Не применяйте миграции вручную в другом Dashboard «для проверки». Для локальной
проверки предназначен `supabase db reset`.

### 3. Выпустить Edge Functions

Если функция менялась:

```bash
npm run functions:deploy
```

После деплоя проверьте:

- `public-menu` возвращает только публичные поля;
- `public-order` принимает заказ и читает статус;
- `public-reserve` возвращает профиль/слоты и создаёт бронь;
- `cardcom-payment` остаётся закрытой (`503` или `501`), пока безопасный поток
  не реализован полностью.

### 4. Выпустить frontend

Push в `main` запускает production deployment Vercel.

Для проверки невыпущенной пары клиентов/схемы сначала отправлять изменения
в `codex/**`: CI запускается без merge в production-ветку. Vercel может
создать отдельный Preview по настройкам Git-интеграции; это не приёмочная
среда, пока для него не проверены изолированные env/БД. Не прогонять мутации
против production через Preview. Перед merge применить совместимую схему
по порядку выше; push рабочей ветки сам по себе миграции не применяет.

После production-публикации:

- откройте `/setup` или `/pin` в чистом браузере;
- проверьте, что manifest и service worker обновились;
- откройте ленивый менеджерский route после деплоя;
- проверьте публичные `/order/:locId` и `/reserve/:locId`, если они затронуты.

`lazyWithRetry` помогает старым вкладкам пережить смену chunk hashes, но не
заменяет smoke-test.

#### Как касса забирает новую версию

Service worker собран в режиме `prompt` (`vite.config.ts`): новый воркер
**ждёт**, пока приложение не пришлёт ему `SKIP_WAITING`. Пока он ждёт, старый
precache цел и работающая касса ничего не теряет.

Приложение (`src/lib/swUpdate.ts`) ищет обновление на старте, при возврате в
приложение, при появлении сети и раз в час; найдя — показывает плашку.
Перезагрузка происходит ТОЛЬКО по нажатию и ровно один раз. Пока открыт чек
или летит мутация, кнопка заблокирована: перезагрузка посреди оплаты стоит
чека.

Чего делать нельзя: возвращать `registerType: 'autoUpdate'`. В нём плагин
вставляет в SW безусловный `self.skipWaiting()` (чужой precache сносится под
работающей страницей), не подключает `onNeedRefresh` вовсе и делает
`updateSW(true)` пустой функцией — обновление превращается в молчаливый
reload в случайный момент. Именно так касса месяцами крутила старый бандл:
в POS-сборке `UpdateToast` не монтировался, и кода про SW там не было
совсем.

Если терминал всё же завис на старой сборке (проверяется в Настройки →
Устройство → «Обновления»): новый воркер активируется, когда отпущены все
клиенты, то есть после ПОЛНОГО закрытия и повторного открытия кассы —
перезагрузок страницы недостаточно. Крайняя мера — «Переустановить
приложение» там же: она сносит Cache Storage и регистрации SW, но не трогает
`localStorage`/IndexedDB, поэтому офлайн-очередь продаж и сессия устройства
остаются.

Отдельный сигнал: если `get_schema_version` вернул номер БОЛЬШЕ
`MIN_SCHEMA_VERSION` этой сборки, фронт отстал от применённых миграций.
Работу не блокируем (в окне релиза так выглядят все кассы), но плашка
обновления становится обязательной и не закрывается.

Языки: production Vercel собирается **без** `VITE_ENABLE_INTERNAL_RUSSIAN` —
касса иврит-only (дефолт `he`, переключатель скрыт, persisted `ru` приводится
к `he`). Не добавляйте флаг в Vercel env: русский — только для dev и
внутренних стендов.

### 5. Выпустить APK при необходимости

Новый APK нужен, если изменилось что-то в `android/`, включая `app_url`.

`app_url` зашивается в сборку намертво: если origin недоступен, установленная
касса остаётся без фронтенда, и починить это можно только новым APK. Перед
выпуском workflow сам прогоняет `npm run check:appurl` (https, не `*.vercel.app`,
origin отвечает 200) — эту же проверку можно запустить локально.

1. Увеличьте `versionCode` и `versionName`.
2. Запустите GitHub Actions → `Android APK` → `Run workflow`.
3. Используйте артефакт `kassa-sunmi-apk-release`.
4. Установите поверх предыдущей версии и убедитесь, что подпись совпадает.
5. Не используйте debug artifact в production.

## Откат

### Frontend

Переопубликуйте предыдущий успешный deployment Vercel. Учитывайте, что новый
service worker может уже находиться на устройствах; проверяйте reload и lazy
chunks после rollback.

### Edge Function

Задеплойте предыдущую проверенную версию конкретной функции. Секреты не
встраиваются в код и должны оставаться в Supabase Secrets.

### База данных

Не делайте destructive down migration и не переписывайте применённый SQL.
Исправление выпускается новой forward-only миграцией. Если frontend уже
откачен, новая схема должна по возможности оставаться обратно совместимой до
завершения инцидента.

Финансовые записи нельзя удалять ради отката. Ошибочные операции исправляются
компенсирующей записью и отдельным аудитом.

### APK

Android обычно не позволяет установить APK с меньшим `versionCode` поверх
нового. Выпустите исправленную сборку с более высоким кодом и той же release
подписью.

## Бэкапы и PITR

Production-проект хранит финансовую историю заведений — резервное копирование
обязательно, это условие эксплуатации, а не опция. Полный runbook (слои
защиты, `npm run db:dump`, сценарии восстановления, верификация, журнал
прогонов) — [backups.md](backups.md); ниже краткая выжимка.

- Ежедневные автоматические бэкапы входят в платный план Supabase; их наличие
  и срок хранения проверяются в Dashboard → Database → Backups.
- Point-in-Time Recovery — платный add-on (Dashboard → Project Settings →
  Add-ons). Включает непрерывную архивацию WAL и восстановление на момент
  времени с гранулярностью до минут. Для кассы с офлайн-очередью это основной
  механизм защиты: суточный бэкап теряет до дня продаж, PITR — минуты.
- Перед крупными миграциями (изменение денежных таблиц, массовые backfill)
  и раз в квартал снимайте логический дамп: `npm run db:dump`
  (project-ref guard → roles + schema + data в `backups/<дата>/`).

Восстановление PITR откатывает **весь проект** на выбранный момент — вместе с
заказами, пробитыми после точки восстановления. Это инструмент катастрофы
(потеря/порча базы), а не исправления ошибочных операций: ошибочные операции
исправляются компенсирующими записями (см. «Откат» выше и правила в
[database.md](database.md)). После восстановления обязательны сверка
фискальной нумерации с последними напечатанными чеками и полный
[smoke-test T2](t2-smoke-test.md).

## Наблюдаемость парка

Телеметрия (миграция 074, `src/lib/telemetry.ts`) даёт две операторские
view в SQL Editor:

- `ops_fleet` — каждое устройство: организация, точка, `app_version`,
  `webview_version`, `bridge_version`, здоровье offline-очереди
  (`outbox_pending`, `outbox_oldest_at`, `outbox_failed`), `last_seen_at` и
  «молчание» (`silence`). Сортировка — давно не выходившие на связь сверху.
- `ops_errors` — свежие клиентские ошибки по организациям: `window`/`promise`
  (глобальные), `react` (ErrorBoundary), `outbox` (стоп offline-очереди),
  `print` (сбой/таймаут печати APK). Повторы схлопнуты в `count`.

Heartbeat уходит раз в 5 минут с открытой кассы; `register_device` дополняет
его при входе и восстановлении сети. На что смотреть при обходе (ежедневно на
одной точке, обязательно после каждого релиза):

```sql
select * from ops_fleet;                                   -- версии и молчание
select * from ops_errors where last_seen_at > now() - interval '1 day';
select * from ops_fleet
where outbox_failed or outbox_oldest_at < now() - interval '30 minutes';
```

Тревожные сигналы: `silence` больше часа в рабочее время (касса не открыта
или без сети), `outbox_failed = true` (очередь стоит, нужен ручной разбор на
устройстве), старый `outbox_oldest_at` (операции не реплеятся), рост `count`
ошибок `print` (принтер деградирует). Стеки ошибок доступны только оператору
(`service_role`).

### Что кассе разрешено отправить в `ops_errors`

Очистка выполняется на клиенте в `src/lib/telemetry-sanitize.ts` **до** записи
в localStorage, до расчёта fingerprint и до RPC. Очередь `kassa-telemetry`
считается недоверенным входом и проходит ту же очистку при каждом чтении:
записи прошлых версий кассы и любой посторонний JSON в этом ключе очищаются
или отбрасываются, а не пересылаются как есть. Принадлежность очереди
конкретному входу устройства держит `src/lib/telemetry-context.ts`.

Гарантируется:

- в payload уходят только поля сервера: `fingerprint`, `source`, `message`,
  `stack`, `route`, `app_version`, `user_agent`, `count`. Посторонние поля
  записи отбрасываются, `source` приводится к списку 074/082, `count` — к
  конечному целому в диапазоне 1…1000;
- из текста вычищаются известные формы секретов и персональных данных: JWT,
  `Bearer`/`Basic`, пары `token|password|pin|apikey|secret|authorization=…`,
  почта, телефон, UUID, длинные непрозрачные строки, `data:`/`blob:`-URL.
  Очистка идёт по всей строке, включая начало: ни класс ошибки, ни «машинный
  код» не считаются безопасными заранее, поэтому `password: …` и `pin: …`
  в начале сообщения вычищаются так же, как в середине. Значение берётся
  в четырёх формах — голое, `"…"`, `'…'` и `[…]`; собственный плейсхолдер
  `[redacted]` отличается от произвольного значения, поэтому повторное чтение
  очереди не меняет запись. Экранированные кавычки не заканчивают значение;
  если закрывающий знак не пришёл или оказался за лимитом входа, оставшаяся
  часть значения удаляется до конца доступного текста;
- URL нормализуется до схемы, хоста и обезличенного пути: userinfo, query и
  fragment теряются всегда (именно там живут `?phone=eq.…` и
  `#access_token=…`); значение из detail Postgres `Key (col)=(value)`
  заменяется на `=([redacted])`;
- `route` — только маршрут: идентификаторы, номера и всё, что не похоже на
  статический сегмент, превращаются в `:id`, `:n`, `:x`;
- `stack` — только кадры (до 8), заголовок стека отбрасывается, а позиция
  `:строка:колонка` сохраняется;
- `user_agent` не обрезается, а пересобирается из узнаваемых частей: продукт
  с версией (`Chrome/52.0.2743.100`), одиночное слово без цифр (`Mobile`) и
  скобочный комментарий платформы (`(Linux; Android 7.1.2; …)`). Посторонняя
  приписка вида `key=value`, URL или нелатинский текст отбрасываются целиком;
- `source` приводится к списку 074/082 в момент capture, до fingerprint и до
  записи: значение приходит из runtime вызывающего кода и доверенным не
  считается;
- диагностика одного входа устройства не отправляется от имени другого:
  запись помечается **поколением входа**, а поколение привязано к тройке
  `user + org + location`. Неподтверждённые и чужие записи удаляются, а не
  досылаются; при выходе поколение закрывается, и повторный вход тем же
  аккаунтом старую очередь не забирает;
- поколение ведёт одна подписка на события Auth, поднятая в `initTelemetry`.
  Выход закрывает поколение сразу и **в offline**: отправка для этого не
  нужна, записи закрытого входа уходят с диска в тот же момент. Повторное
  `SIGNED_IN` и обновление токена того же входа поколение сохраняют, поэтому
  накопленная очередь при рефреше не теряется;
- новая запись метится контекстом, подтверждённым **этой вкладкой**, а не
  тем, что лежит в общем ключе. Если соседняя вкладка уже подтвердила другой
  вход, запись остаётся неподтверждённой и удаляется при ближайшей сверке —
  соседу она не достаётся;
- позднее чтение initial session не перезаписывает более новое событие
  входа/выхода: снимок сессии, устаревший за время ожидания, отбрасывается;
- собранный batch уезжает с токеном той сессии, для которой он собран
  (заголовок `Authorization` ставится явно). Между `getSession` и сетевым
  вызовом SDK успевает перечитать токен, поэтому без этого пакет прошлого
  аккаунта мог уйти с заголовком нового. Если контекст сменился, пока пакет
  летел, поздний ответ не трогает уже чужую очередь;
- очередь ограничена 40 записями и 64 KiB; телеметрия не трогает финансовый
  `kassa-outbox` даже при полной потере диагностики.

Локально касса хранит ровно две записи: очередь `kassa-telemetry` и метку
входа `kassa-telemetry-ctx` вида

```json
{"v":1,"g":"<16 hex>","s":"<16 hex>","d":"<32 hex>"}
```

где `g` — поколение входа (им помечены записи очереди), `s` — случайная соль
устройства, `d` — 128-битный отпечаток `s|user|org|location`. Токены,
`user_id`, `org_id` и `location_id` на диск не пишутся: записи хватает только
на ответ «вход тот же или уже другой».

Сознательно теряется (это цена гарантии, а не дефект):

- текст, который нельзя интерпретировать, обрезается до безопасного префикса
  с меткой `[unsafe]`. Так обрабатываются сериализованный объект (`{…}`) и
  нелатинский текст — там встречаются имя гостя, состав заказа и серверные
  сообщения на русском/иврите. Класс ошибки (`TypeError`) и машинный код
  (`invoice_immutable`, `PGRST116`) при этом сохраняются;
- вместе с query и fragment теряются параметры запроса, включая безобидные;
- ошибки, пойманные до подтверждения входа (первые мгновения запуска, старт
  без сессии), поколения не имеют и удаляются без отправки. То же относится к
  очереди прошлой версии кассы: её владелец неизвестен;
- очередь прошлого входа удаляется при смене аккаунта, организации или точки
  и при повторном входе после выхода. По событию выхода записи закрытого и
  неподтверждённого поколения стираются сразу, не дожидаясь следующего входа:
  отправить их уже некому. Пустое чтение сессии внутри отправки трактуется
  иначе — это переходное состояние (обновление токена, занятый auth lock),
  поколение закрывается, но очередь остаётся ждать;
- из `user_agent` пропадают нераспознанные части строки, включая безобидные
  приписки прошивки.

Ограничения, которые нельзя выдавать за соответствие:

- набор правил закрывает перечисленные формы, а не «любые персональные
  данные». Латинское имя или адрес внутри английского сообщения регулярным
  выражением не опознаются; на такой текст полагаться нельзя;
- отпечаток входа — не криптографический MAC. Он исключает случайное
  совпадение и присвоение очереди соседнему контексту, но не защищает от
  того, кто уже имеет доступ к localStorage устройства. Граница здесь —
  «при несовпадении удалить», а не «доказать подлинность»;
- вкладки одного и того же входа делят один ключ localStorage намеренно:
  их записи принадлежат одному поколению. Записи вкладки с другим входом
  удаляются при первой же сверке;
- если токен сессии истёк, привязанный пакет получит отказ сервера и
  останется в очереди до следующего окна — телеметрия задержится, но чужим
  аккаунтом не отправится;
- правило действует только на новые записи. Строки `client_errors`, попавшие
  на сервер до этого изменения, остаются как есть — их ретенция и защита
  относятся к серверной части F6 и здесь не выполняются;
- на реальном терминале T2 изменение не проверялось: обязателен
  [smoke-test](t2-smoke-test.md) после выката.

### Серверная граница приёма (170)

Клиентская очистка выше — свойство своей кассы, а не граница: `report_client_errors`
принимает произвольный JSON от любого авторизованного клиента. Миграция 170
переносит проверки на сервер, подпись RPC и формат ответа не меняются.

**Принадлежность.** `p_device_uuid` сверяется с `devices` по тройке
`org_id` + `location_id` + `auth_user_id` из JWT. Чужое устройство (другой
сотрудник в той же точке, другая точка своей организации, другая организация)
и неизвестный UUID получают отказ `device_not_registered`; записи от их имени
не создаются и не обновляются. `archived_at` намеренно не проверяется — архив
остаётся косметическим признаком; одна учётка с несколькими `device_uuid`
остаётся рабочей моделью. Digital-аккаунт без `location_id` в JWT кассой не
становится. Удалённая/заблокированная учётка со старым токеном отсекается
ещё раньше, на `auth_org_id()` (169).

**Для кого действует строгая принадлежность.** Проверка тройки применяется к
клиентской роли `authenticated` — то есть ко всему, что приходит через
PostgREST с пользовательским JWT. Для доверенного `service_role` и
операторского вызова (Edge Function, psql под сервисной ролью) проверка
пропускается намеренно: это сохранённая семантика 082/169, на ней держатся
существующие серверные источники, включая `shift`. Org при этом всё равно
берётся из claims — вызов без `org_id`/`sub` получает `not authenticated`, —
но за корректность `device_uuid` в таком вызове отвечает сам серверный код.
`anon` до RPC не дотягивается: `EXECUTE` у него отозван. Иначе говоря, 170
закрывает подделку чужого устройства клиентом, а не ограничивает любую
SQL-роль: тот, у кого есть `service_role`, и так может писать в таблицу
напрямую.

До `register_device` диагностика не принимается: в первые секунды первого
запуска касса получает отказ, пакет остаётся в очереди и уходит после
регистрации. Это сознательный размен — регистрацию нельзя обойти и нельзя
перепривязать чужой UUID, а стоимость ошибки — отложенная, а не потерянная
диагностика.

**Недоверенный JSON.** Верхний уровень обязан быть массивом: SQL NULL, JSON
`null`, объект и строка получают отказ `errors must be a json array` без
записей и без очистки. `NULL` в `p_device_uuid` отвергается тем же
верхнеуровневым исключением — сообщение у этой проверки общее, отдельного
текста про устройство здесь нет. Внутри массива битый элемент пропускается, а валидные
соседи сохраняются — общего `EXCEPTION WHEN OTHERS` нет, настоящий сбой БД
остаётся сбоем. Пропускаются: не-объект, отсутствующий/нестроковый
`fingerprint` или `message`, пустой `fingerprint`. Пустая строка в `message`
остаётся допустимой — контракт 082 здесь не ужесточается. Типы полей
сравниваются через `IS DISTINCT FROM`, а не `<>`: у отсутствующего ключа
`jsonb_typeof` возвращает SQL NULL, и `<>` даёт NULL вместо TRUE. Первая
версия 170 на этом пропускала элемент без `fingerprint`/`message` в `INSERT`
и роняла весь пакет с 23502 — регрессия против 169, закрытая до выпуска
(`supabase/tests/telemetry_missing_fields.test.sql`). Нормализуются:
отсутствующий/`null`/неизвестный `source` → `window` (список 074/082 из шести
значений сохранён); `count` берётся только из JSON-числа и приводится к
1…1000, любой другой тип — это 1; нестроковые `stack`/`route`/`app_version`/
`user_agent` обнуляются, а не сериализуются в текст.

**Лимиты.** Прежние: 20 элементов на вызов, 100 новых `fingerprint` на
организацию/устройство/сутки, `count` 1…1000 и обрезка текстов. Счётчик
повторов насыщается на `2147483647` вместо падения пакета: сумма считается
в BIGINT и подрезается, тип колонки не меняется. 2^31 повторов одной ошибки
за сутки — это шторм, а не счёт, поэтому потеря точности выше порога
осознанная.

**Конкурентность.** Дневной лимит считается `COUNT`-ом и применяется при
`INSERT`; между ними параллельное соединение успевало вставить свой
`fingerprint`, и на 99 строках двое оставляли 101. Теперь на спорный участок
берётся advisory-блокировка пары `org + device` — не глобальная: разные
устройства и организации не сериализуются друг с другом. Одна pgTAP-транзакция
этого не проверяет, для этого есть
`scripts/test-telemetry-ingest-concurrency.mjs`.

**Очистка.** Хвост старше 30 дней удаляется только в своей организации
(`org_id` из JWT) и только после успешной проверки принадлежности: ни
верхнеуровневый отказ, ни `device_not_registered` её не запускают, и строки
чужой организации она не трогает ни при каком входе. Это по-прежнему
**оппортунистическая** очистка: единственный её триггер — успешный приём
ошибок от этой же организации. Гарантированной 30-дневной ретенции в системе
нет. На молчащей организации (касса выключена, заведение закрылось, версия
без телеметрии) записи старше 30 дней остаются лежать неограниченно долго,
и 170 этого не меняет. Cron здесь не добавлен, исторические логи не чистятся;
серверная ретенция и privacy остаются отдельной незакрытой частью F6.

Остаётся незакрытым: свободный текст от старых клиентов, серверная
privacy/ретенция и защита строк, попавших в `client_errors` раньше. Проверка
выполнялась на синтетической БД: SQL-роль и подставленные JWT-клеймы не
равны настоящему GoTrue, production и T2 не проверялись.

Безопасный разбор обращения строится на `source` + `fingerprint` + `route` +
первом кадре стека + `app_version`. Если в `message` стоит `[unsafe]`, нужного
текста в журнале нет и не будет: запрашивайте у заведения шаги воспроизведения,
а не содержимое экрана, заказа или письма. Если устройство «молчит» по
`ops_errors`, но живо по `ops_fleet`, сначала проверьте, не менялся ли на нём
вход: очередь прошлого поколения удаляется намеренно.

Те же эксплуатационные поля устройства (без стеков ошибок) владелец видит в
ANGLE back office → раздел **«Девайсы»**: RPC `get_backoffice_fleet` (097)
отдаёт парк своей организации (право — членство владельца/менеджера, чтение
под RLS), фронт группирует по точке и поднимает молчащие/с зависшей очередью.
`ops_errors` в веб не выведен — это по-прежнему только операторский канал.

## Минимальный post-deploy smoke

1. Вход устройства и PIN.
2. Открытие стартового рабочего экрана.
3. Продажа наличными и получение серверного номера чека.
4. Тихая печать оригинала на Sunmi.
5. Перепечать с пометкой копии.
6. Авиарежим → локальная продажа `K-n` → сеть → sync.
7. Очередь бариста и действие «готово».
8. Открытие менеджерского lazy route.
9. Проверка публичных страниц, если менялись функции/настройки.

## Наблюдение за инцидентом

При проблеме зафиксируйте:

- commit и version приложения;
- Supabase migration number;
- URL/версию deployment;
- модель терминала, Android и Chrome/WebView major;
- online/offline состояние и содержимое offline sheet без персональных данных;
- тип печати: APK, RawBT или browser;
- server error code и client UUID проблемной операции.

Не копируйте в тикет access token, anon/service keys, PIN или полный payload с
телефоном гостя.
